# 天气多来源、多城市与多格子并存

本决策替代 [ADR-0025](0025-天气组件可选来源与网页详情.md) 中的单一启用来源条款；来源接入、凭据安全、缓存、计费与署名边界继续按 ADR-0025 执行。

## 已确认决策

天气来源不再有“当前启用来源”。设置中可以同时配置并使用多个来源，每个来源一条独立凭据记录，互不替代；每个来源在设置中维护自己的城市或地区列表，每个桌面天气格子保存自己使用的来源与城市。同一个来源可以被多个格子使用，同一个城市可以同时出现在多个格子，桌面可以同时显示不同地区、不同来源的天气。

- 删除普通偏好 `weatherSource`；来源归属改由格子自身携带，不再由全局偏好决定请求目标。
- 设置页来源列表移除行尾启用开关与“当前使用”文本，行内保留来源名、服务地址、认证模式、可用状态与进入编辑的箭头。
- 每个来源的城市列表按来源分文件保存在配置目录，只保存用户显式添加的 `City` 对象，不保存来源的搜索结果集合，不进入普通偏好、工作区快照或日志。城市列表项可以删除，删除只移除该项，不改变已存在的格子绑定。两个来源使用同一套按来源文件的城市列表，不为任一来源另设仅会话内存的城市列表：该决策按“用户自带账户、本机自用、数据量级极小”的风险认知做出，供应商条款的书面澄清仍待补充。
- 天气格子的组件 `state` 只保存 `weatherSource` 与 `weatherCityId` 两个标识，不保存城市对象。格子切换来源时清空自己的城市配置，必须重新选择城市；格子绑定的城市从来源列表删除后，格子进入待重选状态且不自动改选其他城市。
- 设置中的城市添加入口为四处：来源右键菜单的“添加城市”、来源列表展开区末行的“添加城市或地区”、编辑弹窗城市列表末行的“添加城市或地区”、天气格子右键菜单“选择城市”二级菜单里的“添加新城市或地区”。添加 API 的弹窗只填写凭据，不提供城市入口，城市在保存后从编辑入口或来源入口添加；四处共用同一城市弹窗。城市项的删除在来源列表展开区与编辑弹窗的城市列表各有一个入口，两者共用同一确认；删除图标直接进入确认，右键先展开只有“删除”的城市菜单，选中后才进入同一个确认框，右键不直接执行删除或弹出确认。桌面侧“添加新城市或地区”在写入列表的同时把该城市绑定到当前格子。
- 城市删除成功后，后端通过既有的天气配置变化通知广播一次无数据事件，不新增事件通道：已展开的桌面格子收到后立即重读该来源城市列表，绑定被删城市的格子进入“该城市已从列表移除”状态并停止请求与活动订阅，不再等待用户下次打开菜单。新增城市不广播，因为格子菜单打开时已按来源重读列表，广播只会带来一次无意义的缓存清空与请求。
- 城市列表改动的提交边界按入口区分：来源展开区与来源右键菜单的添加/删除立即落盘，因为它们没有自己的保存按钮；编辑弹窗里的添加与删除只记在本次编辑的草稿里，点“保存”时才与凭据改动一起提交，取消或关闭即丢弃。理由是编辑弹窗有明确的保存/取消语义，若城市改动即时写入，用户点“取消”后城市列表已经不回去了，与同一个弹窗里凭据改动必须保存才生效的规则不一致。编辑弹窗的草稿用“已保存项减去待删除、加上待添加”推导，不需要第二份城市数据。
- 城市列表的刷新只有一个权威来源：展开区与编辑弹窗都按本次命令返回值刷新，展开区不再单独持有“当前展开的城市数组”，避免同一份列表在两处各走一条更新路径而漏刷新。
- 城市弹窗只有一份实现，提取为独立文件：来源右键菜单“添加城市”、来源列表展开区“添加城市或地区”、天气格子菜单“添加新城市或地区”都复用同一个弹窗组件，标题、主命令文案与状态文案由调用方传入，搜索、验证与确认行为由调用方提供。同一功能的弹窗不再按位置分别实现或复制 DOM 与样式。城市项的删除统一使用图标库的 `trash` 图标资源，不使用文字“删除”。
- 天气格子由用户显式创建。桌面空白处右键菜单提供“添加天气”，创建的格子初始不绑定来源与城市，由格子内容区按缺失状态提示选择来源或城市；来源右键菜单的“添加天气格子”二级菜单按城市创建已绑定来源与城市的格子。不再向工作区注入默认天气实例，也不在布局恢复时补回天气格子，天气格子与收集箱一样可以移除。
- 功能格子列表中的天气开关保留为天气格子的整体显隐开关。创建天气格子时若该开关处于关闭状态，由创建入口在同一偏好保存链路中写入开启并广播偏好变更，避免出现“已创建但不可见”的格子；创建动作不使用格子的可见性作为成功条件。
- 创建与移除组件的白名单扩展为天气格子，与收集箱共用同一创建入口与布局事务，沿用布局撤销。

来源隔离细化到运行期键与配置代次：预报退避、活动实例计划、在途请求与配置取消标记都以来源为前缀，`(来源, 城市)` 相同的实例共享一次请求，来源之间互不取消、互不覆盖同名城市；磁盘预报缓存继续按配置指纹与城市标识保存，不因新增来源而改动格式。

来源隔离靠“所有入口显式携带来源”实现：取数、缓存读取、城市搜索与活动调度入口都接收来源参数，按来源解析凭据记录、城市列表路径与配置代次，不保留“当前启用来源”这类运行期单值。这条约束的代价是每个入口多一个参数、每处调用方都要给出来源，换来的是来源归属不可能被运行期状态悄悄改写。

城市边界校验拆分为两层：坐标、时区、标识与长度等公共规则由天气模块统一执行；城市详情链接规则移入各来源实现。没有城市天气网页的来源允许空的详情链接，其“查看详情”入口按链接为空保持禁用，不计为验证失败。

天气数据解析的信任边界放在 Rust：已绑定城市的读取只提交来源与城市标识，城市对象由 Rust 从该来源的城市列表解析，`(来源, 城市)` 的失败判定、退避记录与缓存归属也在同一处完成。前端不自行判断城市是否仍在该来源列表中；把已绑定城市的读取输入收敛为两个标识后，“城市必须来自该来源的城市列表”成为单一不变量。

按已保存凭据添加城市时，命令额外接收搜索返回的候选 `City` 对象：该候选尚未进入任何列表，Rust 无从按标识解析，因此由 Rust 执行公共与来源边界校验后写盘，前端不参与坐标、时区与详情链接的合法性判断。

城市写入只发生在用户确认添加时：搜索得到候选、可选的验证只返回可用性结论，都不改动城市列表；点“添加”才按上述命令写入。理由是两个来源官方文档对“搜索命中”的证明力不同——Foreca 位置搜索返回的 `id` 在官方 schema 中标注为用于天气查询的位置标识，其 `/api/v1/current`、`/api/v1/forecast/*` 都接收该标识，搜索命中即等价于该位置可用于天气接口，失败只剩凭据、套餐与 QPS 一类与城市无关的原因；和风的位置搜索只证明该 LocationID 存在，官方错误码另列 `400 DATA NOT AVAILABLE`（该位置不支持所查数据）与 `403 FORBIDDEN`（无该数据权限），凭据还可配置 API 限制，因此和风必须真的发一次请求才能判断可用性。城市验证命令据此按来源执行：搜索命中即可证明可用的来源只执行字段与详情链接校验，其余来源用该来源已保存凭据请求一次当前天气，失败原因与可用状态同探测共用；验证仍不写入城市列表，也不作为添加的前提。

保存之后的可用性检查对两个来源执行同一条路径，用该来源列表中第一座城市请求当前天气；来源还没有城市时退回固定探测位置。检查结果写回来源可用状态并呈现给用户，但不阻止凭据写入：凭据记录的有效性与某个具体城市的可用性是两件事，写入失败会让用户在额度或网络短暂异常时无法保存配置。保存动作本身不等待这次网络请求——验证是保存后的独立一步，弹窗先收起，结论稍后补到可用状态与状态行，避免保存按钮被一次超时（连接 8 秒、总 20 秒）压住。保存后不做检查的来源会因保存时清空可用状态而长期停在“未确认”，因此不为某个来源设置这项豁免。

两个来源的保存、编辑、城市管理与探测共用同一条实现，只有请求层按来源分派。差异只允许存在于三处：请求层（端点、认证方式、响应结构与错误码）、来源表里的展示与回填内容（显示名、认证模式、字段集、底栏署名），以及来源固有规则中写在共享函数里的一个分支（例如和风要求城市带详情链接）。其余任何位置的按来源分支都视为缺陷：新增来源时只应改这三处。前端不得按来源名特判字段是否允许留空、是否执行保存后检查、字段如何回填，这些一律由字段表与来源表表达。

限流等待按来源记账：一个来源被服务端要求等待时，只拒绝该来源发起的请求，不影响其他来源的搜索、验证与探测。可用状态、配置代次、城市列表与预报退避已经按来源索引，限流等待必须同样按来源索引，否则一个来源的 429 会连带拒绝另一个来源的操作。

天气状态锁必须保持“只在一处持有、不重入”：`execute` 全程持有状态锁，期间任何再次加锁的取值都必须直接从已持有的守卫读取。配置代次、可用状态与作废这套记账因此实现为 `Inner` 的方法，只在已持有守卫时可用，由编译器而不是注释来保证不会二次加锁。该缺陷的表现是探测线程永久阻塞并一直持有锁，后续任何读取状态锁的命令都会挂住调用线程，其中 `list_weather_sources` 是同步命令，会直接挂住整个程序的主线程，表现为托盘与退出全部失去响应。

来源列表的一次读取同时决定“是否已配置”与回填内容，不再先查存在再读内容：两次读取之间失败会得到地址为空、字段缺失的半残行。本次读取失败只把该来源排除在这一次列表之外并记录日志，不让状态查询整体失败——取消与状态类命令也会构建该列表，整体失败会把无关操作一起打断。

命令面按调用方分两条通道：设置窗口经 Tauri `invoke_handler`，桌面宿主经原生 `dispatch_native_command`，两者各自登记。城市搜索、验证与写入都按来源显式表达，只使用已保存凭据，不进入设置会话草稿；桌面宿主与设置页共用这三条按来源命令。完成创建天气格子的入口位于 Rust，功能开关的开启与组件创建走同一条偏好保存链路，使桌面、来源菜单与 Explorer 三个创建入口共用该行为，不依赖前端先存偏好。

创建与移除的判定依据是插件清单自己声明的能力，而不是工作区里针对插件身份的判断：清单声明该插件是否可由用户创建、是否可移除，缺失视为不可创建且不可移除，工作区按声明执行并沿用同一创建入口与布局事务。理由是可创建插件已出现第二个，按身份硬编码会在每新增一个可创建插件时重复一次。

天气插件清单的持久化版本与天气格子实例的状态版本都保持 1，格子状态只新增标识字段、不递增版本、不写迁移：实例版本与清单版本比对失配的实例会被判定为不可用，抬高版本会让已有布局中的天气格子无法加载，而缺失字段已经能表达“未选择”。

## 原因与职责边界

多来源并存来自一个自然诉求：同一台机器上不同来源的覆盖范围、配额与可用性不同，用户可能同时需要国内城市与国外城市。把这层选择上移到每个格子，可以让来源归属、城市归属与显示位置一一对应，避免继续用“全局一次只启用一家”的表达去模拟多来源，也避免全局城市文件让所有格子显示同一地区。

城市列表由用户显式维护，而不是从搜索结果或格子配置反推：搜索结果按供应商要求不落盘，格子配置只存标识，只有显式添加的列表才能同时承担“设置页可见可管”“格子菜单可直接选择”“重启后仍可用”三个职责。

格子只保存标识而城市对象集中在来源列表，是为了让同一城市在多个格子、重启与缓存读取之间只有一个权威来源，也让来源隔离规则只需要在一处表达。

不引入来源自动故障切换、不拼接两家数据、不自动定位，也不新增来源优先级或权重配置；同时使用多个来源由用户在不同格子上分别选择，产品不替用户决定取哪一家。

## 待验证假设

- Foreca 的城市列表与天气落盘采用与和风相同的按来源文件模型，该来源的缓存与城市持久化仍未取得供应商书面说明，已按本机自用的风险认知接受，尚未在真实账户上复核条款适用范围。
- Foreca 位置搜索只覆盖城市级，用户选择“地区”在部分国家可能只能落到所属城市；城市列表的显示文案需要按来源实际返回的行政区字段降级显示。
- 城市列表长度、多个格子共用同一来源时的请求合并效果、来源与城市数量增长后的调度表现，均需在真实账户与真实宿主上验证。
