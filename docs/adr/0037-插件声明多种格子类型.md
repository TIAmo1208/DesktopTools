# 插件声明多种格子类型

## 背景

插件清单当前只能声明“这个插件能创建格子”，一个插件下的所有实例使用同一份外观与同一套内容。需要在一类数据上用不同粒度呈现时（例如服务连通状态、消息数、Token 用量来自同一份快照），作者只能让每个格子自行判断该画什么，用户也无从在同一次创建里选择。本决策让清单声明格子类型，并让创建入口按类型展开。类型、上限与入口的改动已在开发构建中完成人工验证。

## 决策

### 声明

清单 `manifest.ini` 新增 `[tiles]` 节，每行 `键 = 显示名`：

```ini
[plugin]
id = plugin.example.multi
name = 示例-多类型
version = 1.0.0
entry = index.js
creatable = 1

[tiles]
status = 连通状态
messages = 消息数
tokens = Token 用量
```

- 键是作者代码里的稳定标识，按与组件标识相同的字符集校验：ASCII 小写字母、数字、`-`、`_`，长度不超过 32；显示名去掉首尾空白后为 1 到 24 个字符，按序排列。
- 第一节就是默认类型。
- 子节存在但没有任何有效行时，整份清单按非法处理并进 `failures`：声明了类型却不给类型是作者写错，静默回退会掩盖它。
- 重复键、非法键、非法显示名同样拒绝整份清单。
- 没有 `[tiles]` 节的插件保持原状：视作只有一个隐式类型，键为 `default`，菜单不展开。

### 与创建、移除声明的关系

- `creatable`、`removable`、`maxTiles` 仍按插件身份声明，不随子节改写。`creatable=0` 时子节不生效。
- 子节非空时以子节为准；`creatable=1` 但没有子节时按隐式单类型处理，旧插件不受影响。
- `theme` 角色的插件同样可以带子节，只在入口脚本存在、清单放行创建时生效。

### 类型随实例下发

创建时把类型写进实例 `state`：`{"tileType": "<键>"}`，与天气格子把来源写进 `state` 是同一做法。不新增实例字段，不改快照结构、`stateVersion` 与外观键 `component:<instanceId>`。任一插件创建入口的 `state` 从空对象改为携带类型；没有选择时写第一节的键。

前端把 `state.tileType` 解析后放进外壳上下文 `{ pluginId, instanceId, tileType, collapsed, settings, saveSettings }`，缺失或不是字符串时按 `default` 给空串。插件按 `tileType` 画不同内容。类型是实例的属性，运行时不能改：换类型等于删掉再建。

### 创建入口

- 二级页右上角的添加命令：只有一种类型时仍是加号按钮；多类型时变成下拉按钮，点开列出全部类型，选择一项创建。停用、已达上限时按钮整体不可用，与现状一致。
- 一级页插件行的右键菜单：只有一种类型时仍是单个「添加到桌面」项；多类型时该项变成二级菜单，逐项列出类型。
- 两个入口按同一条规则：键在 `tileType` 中，显示名为菜单文案，同一套创建事务。位置避让、撤销记录和创建成功提示均沿用现有逻辑。

### 数量上限按类型分别计算

- `maxTiles` 仍是单独声明的字段，不改名、不挪进子节；它不是整份清单的共用额度，而是每个格子类型各自的上限：某一类已满只禁用这一项，其余类型照常创建。
- 上限校验对所有创建入口统一生效，读的是实例 `state.tileType`：缺失或空串按清单第一节（默认类型）计，清单没有 `[tiles]` 时按插件身份整体计一个桶。旧插件与旧工作区因此保持原有行为。
- 前端入口按同一口径逐项计算剩余额度：二级页加号在全部类型都满时才禁用，悬停说明按各类剩余最少的一类报数；右键菜单的每一项单独判断，已满的项带「已达上限（N 个）」说明。
- 上限只在用户创建时判定。作者在插件内调用宿主能力补建实例、或撤销把旧实例恢复回来时，不按类型重新计数。

### 外壳契约以外的呈现

类型只影响内容，不影响外壳：格子尺寸、最小尺寸、折叠行为、默认位置都不按类型区分。类型级尺寸不在本决策范围内。

## 原因与职责边界

类型是作者对自己插件内容的划分，放进已有的版本化清单，使“有哪些类型”成为插件自己的事实，宿主不需要为每个插件写分支。把类型做成一等实例字段会牵动快照、外观与撤销，收益不足以抵消改动面；`state` 已随实例持久化并进入撤销，复用它是最小改动路径。

数量上限按类型分别计算：作者让同一份数据出三种粒度时，共用额度会让“只要一个消息数”的用户被另外两个类型占掉名额，而这正是引入类型的动机。校验只读 `state`，工作区、命令与前端都按同一个键归属，不新增字段也不新增快照结构。

本决策不引入类型级权限或类型级能力声明。作者代码仍是受信代码，类型只是一段字符串，宿主不对类型做内容渲染。

## 后果

- 插件自行区分并渲染类型；类型缺失时插件必须回退到默认，不能假设宿主一定给了。
- 同一插件的不同类型实例共用一份 `settings` 与一份注册对象，作者要为共用的定时器与订阅按 `instanceId` 去重。
- 旧插件与旧工作区不需要迁移：没有 `tileType` 的实例按默认类型计入，渲染时插件拿到空串自行回落。
- 上限按类型分开后，同一插件可创建的格子总数取决于类型数 × `maxTiles`；作者仍按“每类几个”写清单，不需要为总数另设字段。
- 类型沿实例固定到删除为止：作者改写清单的类型集合后，旧实例保留原来的键，渲染与新计入都按它处理，不自动迁移。

## 待验证假设

- 设置变更触发重绘时 `state` 随实例重新下发，`tileType` 不变；尚未在真实运行中验证。
- 清单在运行期不重新读取类型，作者改 `[tiles]` 后旧实例仍带原类型键；这类实例落到哪个桶、是否需要清理，尚未在真实运行中验证。
