# 系统通知并入统一消息通道

## 背景

浮岛此前只显示本程序自己投递的消息（原生 Toast 队列与浮岛侧天气、收录通知）。用户希望把其它应用（微信、飞书、DSH 等）的系统通知也显示到浮岛，读取「来源、文本、时间、应用 Logo」。调研结论：公开的 `UserNotificationListener` 只提供应用身份、应用 Logo、创建时刻与文本元素，读不到逐条 `appLogoOverride`、自定义载荷或 `<progress>`；未打包进程可能需要包身份与用户授权才能稳定监听。

## 决策

- 系统通知不新建第二套消息接入：新增的只读条目并入既有消息通道的同一份投影与同一事件（`island-messages-changed`），与原生 Toast 共用同一枚消息通知锚点、同一 hover 列表与同一展开消息卡。
- 消息通道契约补充可选参数：`progress`（确定的 `0–1` 进度，供本程序消息使用）、`iconUrl`（应用 Logo 数据 URL）、`external`（只读系统通知标记）。旧载荷不带这些字段时投影形状不变。`publish_message_notification` 也接受 `progress`，后续来源可以注入确定进度。
- 读取在独立线程按固定节奏轮询通知中心快照：通知中心只保证枚举当前通知，未提供可靠的新增事件契约；授权请求回到 UI 线程执行，未获授权、读取失败或身份缺失时只停止系统通知来源并记录一次日志，不影响本程序消息与其余功能。
- 条目映射：来源用应用显示名，正文用 ToastGeneric 文本元素按显示顺序以「 · 」连接，时间用创建时刻，图标用应用 Logo（限 512 KB 与受支持位图签名，转数据 URL）；条目身份为「应用 AUMID + 系统通知 Id」，同一身份更新内容不换锚点。
- 关闭系统通知条目只从浮岛投影撤下并记住身份，不调用系统通知中心的移除；该通知从系统通知中心消失后解除忽略。系统通知最多保留 16 条最近条目，避免无限增长。
- 胶囊锚点与 hover 列表在有应用 Logo 时显示 Logo（`20 × 20` 安全区），没有时沿用类型图标；展开消息卡同理。加载态没有确定进度时统一使用 `resources/loading.svg`，有进度时用进度环。

## 原因与职责边界

系统通知是外部只读事实：浮岛只能读取、排序与展示，不能代替来源应用完成动作，也不能回写通知中心。把它并入同一消息通道，浮岛与消息锚点就只需要理解一种条目形状；新增的 `progress`、`iconUrl`、`external` 都是可选注入，不会改变已有消息的解析与渲染。

原生负责读取、映射与去重；渲染层只消费统一投影。系统通知条目的关闭属于浮岛本地行为，原生 Toast 的离场命令不受影响。

## 约束

- 不新增系统通知中心写入、撤回或清除调用。
- 不把系统通知的正文或 Logo 落盘、不广播给插件。
- 读取失败不阻断启动，不反复请求授权；同一故障只记录一次。
- 不新增颜色与图标风格：Logo 与类型图标都落在既有 `20 × 20` 安全区，加载图沿用现有 mask 着色方式。

## 已知边界与待验证

- 未打包进程能否获得通知访问授权、`RequestAccessAsync` 在真实机器上的表现、`GetNotificationsAsync` 的返回范围与时机都未在真机确认；未授权时浮岛只显示本程序消息。
- 公开接口读不到逐条自定义图标与进度，因此系统通知条目一律为普通信息类型、无确定进度。
- 来源应用是否真的发送系统 Toast（而非自绘弹窗）决定它是否会出现；不从聊天内容或窗口抓取推断。
- 应用 Logo 为异步读取，超时或格式不支持时该条目没有图标；同一条目 Logo 读取失败不影响正文与时间。
- 去重只按「应用 AUMID + 通知 Id」；应用重建通知会得到新身份。
