# Desktop Tools 正式项目架构

## 问题说明

Desktop Tools 当前通过透明桌面宿主、逐屏 WebView2、混合 DPI、桌面接管、交互命中、围栏操作、Explorer 重启和 guardian 恢复提供核心桌面能力。项目按功能职责拆分宿主、Shell 访问、布局状态、前端呈现和恢复流程，避免平台细节与领域行为相互泄漏。

当前架构需要同时满足以下事实：

- Desktop Tools 拥有桌面项目的呈现与交互，Windows Explorer 提供桌面命名空间、Shell 操作和恢复兜底。
- React/WebView2 负责视觉状态和交互意图，Rust 负责领域规则、Windows 能力和应用生命周期。
- Shell 项目身份与 Desktop Tools 自有布局分别维护，Shell 返回结果作为文件操作事实来源。
- 每台显示器拥有独立透明桌面宿主，宿主需要维护物理工作区、DPI、WebView2 栅格化比例和交互命中图。
- 启动失败、正常退出、Explorer 重启、主进程崩溃和宿主失效都需要进入统一恢复契约。

## 解决方案

原生消息通过 `include_bytes!` 嵌入 `resources/loading.svg`，使用关闭默认可选特性的 `resvg` 解析并按 DPI 栅格化一次，再缓存为 Direct2D Alpha 蒙版；旋转由 Direct2D 变换完成，主题色由现有画刷提供。这样保留软件 DC 合成路径，不为 SVG 引入新的窗口或每帧创建图形设备。

消息队列由 Rust `notifications` 模块维护，使用主显示器上的无激活顶层 HWND。`state` 管理有界队列与每条消息的独立动画，`surface` 缓存 Direct2D 软件 DC 目标、DirectWrite 格式与文本测量，窗口入口协调设置、DPI 和输入。预乘 Alpha 位图通过 `UpdateLayeredWindow` 提交；整窗 Alpha 固定，每条消息独立改变透明度，避免新消息使整个堆栈闪烁。调用参数 `durationMs` 表达正整数毫秒期限；前端入口缺省为 4000ms，但原生请求始终携带明确期限。期限独立于队列顺序，悬停暂停；短消息可先于早入队长消息退出。仅过渡或可见 loading 期间请求连续帧，loading 每秒一圈、约 30 帧，折叠后层或关闭有效动画时停止旋转刷新。稳定时等待最早过期项，空队列停止计时器并释放绘图缓存。

默认折叠只露出两层旧消息表面，悬停展开队列并暂停自动关闭。新增、关闭、悬停变化从各条消息当前呈现状态衔接；进入从下方 16 DIP 向上渐入，退出反向执行，均为 250ms；旧层同时缩小上移或补位。关闭命中使用已提交画面，折叠后层与离场项不响应关闭。Toast 消费 `PreferencesProvider` 已解析的界面深浅色和有效动画结果，不读取系统颜色、不订阅系统主题，也不接收 Windows 强调色回调；字体、字号和圆角仍使用已保存偏好。跨窗口上报须与当前已保存偏好一致，迟到页面不能覆盖新设置。外观变化不重置队列或计时。该边界不包含拖拽关闭、Promise 更新或键盘焦点扩展；透明背景及 SVG loading 动画观感已获用户实机确认，系统主题切换及混合 DPI 等剩余范围见[原生消息验收](../validation/原生消息验收.md)。

消息测试组件只挂载在既有 Debug 格子内部，复用正式消息管道及 Rust Debug 注册边界，避免正式桌面暴露测试命令；不单独创建桌面固定工具栏或测试消息队列。

正式项目采用单应用双边界架构：

1. React 前端按产品功能组织工作区、桌面项目、围栏、文件夹门户、组件和设置，并通过类型化桥接层表达命令与事件。
2. Rust 后端按桌面宿主、Shell、工作区领域、持久化、组件运行时和恢复组织功能模块。
3. Tauri 命令与事件边界作为前后端最高层测试边界，承担参数校验、快照发布和结果回传；平台实现留在 Rust 的 Windows 适配层。
4. Shell 适配器在专用 STA 操作代理中运行，宿主线程持有对应 HWND 和 OLE 生命周期。
5. 独立 Rust 守护进程 负责接管前的状态登记、运行期间观察和异常恢复；业务状态、布局和 Shell 操作结果由主进程持有。
6. 当前源码、契约测试、事实文档和 Windows 验收证据共同构成行为依据，不维护独立参考实现。

桌面项目模块通过组件挂载与释放登记系统图像，向桌面宿主提供解码计数；宿主组合接管门槛，不依赖图像组件内部选择器。`MusicWidget` 位于音乐模块，持有媒体订阅、重试、代次隔离和命令生命周期，通用组件宿主只装配实例及接收尺寸结果。

本地与跨屏项目拖动共用桌面项目模块的预览内容入口。跨屏 Hook 管理会话、消息和过期清理，目标工作区 DOM 适配器集中处理命中、围栏滚动与插入预览，呈现模块负责拖动内容。设置契约只校验数据格式，应用设置层解析环境变量与实际路径，并在偏好及关联布局写入前完成完整校验。用户设置加载忽略 `ApplicationPreferences` 中未知的顶层字段，使已删除且不影响安全和数据一致性的旧偏好不阻塞启动；当前已知字段、枚举、数值范围及嵌套对象仍按现有契约严格校验，后续保存只写当前字段。

## 发布运行边界

原生桌面宿主的 `desktop-host-snapshot-changed`、`workspace-snapshot-changed`、`desktop-item-snapshot-changed`、`component-runtime-snapshot-changed`、`music-session-changed`、`preferences-changed`、`windows-accent-color-changed`、`component-host-event` 和 `folder-portal-changed` 由既有 Tauri 事件源转交主线程 Wry 页面。当前通用快照桥先建立接收入口再读取快照，在途初始读取被新事件超越时丢弃，取消订阅后拒绝迟到交付；暂停不积压视觉事件，恢复补读最新快照。门户目录通知属于独立订阅路径，不能据此推断其已具备相同的初始化与恢复保障。全局权威状态继续按显示器映射投射，不能将完整工作区误过滤为单屏事实。音乐由 WinRT 当前会话、会话集合、媒体属性和播放状态事件唤醒并缓存快照；仅在会话变化、播放状态变化、上一曲或下一曲动作及页面恢复等可能存在系统事件时序差的节点执行有限收敛检查，不在空闲期间持续轮询。门户目录由 `ReadDirectoryChangesW` 通知完整事实重读。Renderer 心跳、guardian 和环境健康检查独立保留。

桌面刷新策略在 Windows 层维护运行期前台状态快照，分别记录外部焦点、最大化、逐屏工作区与整屏覆盖、全屏证据、锁屏状态、查询有效性和修订号；未知状态不编码为 false，也不写入磁盘。命令层将结构化快照交给页面，页面结合已保存偏好计算逐屏策略，继续回报每台显示器实际应用的暂停状态。原生桥接由前台、窗口、Alt+Tab 切换、页面恢复、解锁和显示器变化事件触发采样；切换期间合并事件并延迟提交，采样失败或前台在采样中变化时只进行有限次数复查，不使用无限轮询。候选暂停期间以 350ms 定时复查，触发持续至少 300ms 后暂停视觉交付。页面指针交互、原生菜单和拖放命令期间延后暂停。锁屏优先暂停所有界面的非必要刷新，解锁后重新采样再按设置恢复。设置窗口不参与普通窗口暂停。页面没有挂起，watchdog 沿用原有真实心跳故障检测。

保留 WebView 与后端监听以降低恢复成本，暂停门户通知触发的非必要目录重读和已有 Web Animations，不承诺释放常驻内存或冻结所有第三方媒体解码。原生消息窗口直接消费同一前台状态快照；全屏或锁屏时不弹出消息，停止动画、计时和绘制缓存，恢复时只显示仍未过期的队列项，不补弹历史消息。全屏证据同时支持窗口覆盖和系统通知状态；系统通知状态不能归属到具体显示器，也不承诺准确区分独占与无边框模式。未知窗口、DWM 查询失败、透明分层窗口的覆盖不作逐屏全屏暂停判断。内存收益、真实恢复延迟和复杂 Shell 窗口识别仍须实机验证，不能由单元测试推断。

### 门户、时间与音乐订阅生命周期决策

以下为已确认的实现约束，不是完成声明。门户恢复补读、监听故障重连、初始化与读取竞态隔离，以及活动时钟订阅均须完成对应验证后才能交付。

- 门户桥接层统一管理目录事件、暂停恢复通知和故障重连。初始化顺序为建立前端接收入口、建立目录 watcher、读取初始快照；订阅身份返回前收到的通知应保留为待重读标记，避免握手期间漏更新。后端监听启动成功须表示通知接收已就绪，而不只是线程已创建。部分初始化失败释放已建立资源，正常退订、目录切换和宿主销毁拒绝迟到回调。
- 暂停保留有效目录 watcher，不执行视觉目录重读，不积压历史通知；恢复立即读取当前目录。初次建立失败或收到监听终止错误后，释放旧订阅，仅在失败状态下按 1、2、5、10、30 秒封顶的间隔重连。暂停停止重试计时，恢复或手动刷新立即尝试重建；成功后停止重试并读取最新目录。此兜底用于目录删除、磁盘或网络路径不可用等无法持有可靠事件源的情况，正常状态不轮询；错误沿用现有通知去重与日志，不新增界面。
- 每个门户最多保留一个在途读取，连续通知合并为一次待重读标记。目录切换、暂停和卸载使旧请求失效，读取结果必须匹配当前目录身份及请求代次才能写回。变化在读取过程中到达时，再读最终状态，避免旧结果覆盖新目录，也避免通知突发产生并发完整枚举。
- `LocalClock` 持有时间状态与订阅，`OfficialComponentHost` 和 `ComponentSurface` 不接收或传递周期时间值。活动资格采用授权、功能开关、实际展开状态及所属宿主暂停状态；隐藏内容保留挂载，只停止时间消费。首次活动、展开和恢复均立即读取当前时间，再接收周期事件，不等待下一次 tick。
- 后端组件运行时按独立订阅身份登记活动时间消费者及所属宿主，使用一个共享计时线程。没有消费者时阻塞等待订阅变化，有消费者时按既有一秒周期发布；只向存在活动消费者的宿主交付时间事件。首次登记前建立接收入口，退订、宿主重载和销毁清理对应身份，旧身份的迟到退订不得删除新订阅。既有实例与时间能力校验继续由组件运行时负责，音乐沿用自己的媒体事件。
- 音乐监听线程保留 `CurrentSessionChanged`、`SessionsChanged`、`MediaPropertiesChanged` 和 `PlaybackInfoChanged`。普通空闲状态阻塞等待系统通知，不设置常驻媒体轮询；需要收敛时复用同一监听线程和通知通道，按立即、250ms、1s、3s读取完整快照，连续两次相同即停止，最晚在3秒检查后结束。新的系统事件立即读取并重新开始当前收敛过程。
- `CurrentSessionChanged`、`SessionsChanged`、上一曲或下一曲动作、页面从暂停恢复，以及可能先于媒体属性到达的 `PlaybackInfoChanged` 启动收敛检查。显示器暂停不停止 Rust 的 GSMTC 监听和权威缓存更新，只过滤该显示器的视觉事件；恢复由既有 `resumePolls` 立即调用 `get_current_music_session`，读取缓存最终值，不重放历史事件。
- 音乐媒体协议保持现有完整快照结构，不增加修订号、序号、时间戳或高版本优先规则。Rust 读取继续由单一工作线程串行执行，`MusicWidget` 保留现有组件生命周期和异步取消保护，不增加前端轮询。

选择上述边界是为了在保留事件源和恢复能力的同时，将读取与渲染限制到真实消费者；不新增持久配置、第三方依赖、通用事件框架或每实例计时线程。Shell STA 通过请求事件与消息队列联合无限等待。宿主环境协调由显示变化、Explorer 桌面窗口重建和桌面图标设置变化事件唤醒，事件到达后执行有限收敛检查；只有缺少可靠事件源的单项保留低频故障兜底。guardian 将桌面图标设置注册表变化事件与主进程、正常停止事件共同无限等待。Renderer 心跳与 watchdog 保持现有机制。

验收必须覆盖暂停期间目录变化与恢复、初始化时变化、目录删除后重建、监听失败与恢复、批量变化合并、导航乱序返回、退订及宿主重载；时间事件须覆盖无活动时钟、多时钟共享来源、仅音乐屏幕、折叠与临时展开、单屏及全部暂停和恢复。自动检查不能替代 Windows watcher 故障恢复和实际渲染次数验证；真实资源收益仍待同构建、同布局测量。

Tauri 开发模式与 Cargo 优化 profile 独立。发布构建必须启用 `custom-protocol`，使设置窗口与逐屏宿主共同加载内嵌前端资源，避免运行时依赖开发服务器。使用 Tauri CLI 作为常规发布构建入口，直接调用 Cargo 时显式传入该 feature 并先构建前端。

Release 主程序及 guardian 使用 Windows GUI 子系统，日志仅写文件，控制台等级设置不能恢复 Release 控制台输出。该约束避免正常桌面运行弹出日志窗口；开发构建保留控制台诊断。设置窗口不在启动时创建，由托盘或桌面菜单按需创建唯一 main 页面，关闭时销毁，再次打开重新读取偏好；桌面宿主继续运行，无显式退出码的最后窗口关闭不触发桌面清理。此生命周期用于释放未使用页面，实际进程和内存回收量待实机验证，不改变桌面接管门槛。


## 目标文件结构

本节为职责布局；文件夹门户契约见 [ADR-0019](0019-文件夹门户采用路径绑定与原生文件操作.md)，尚不能视为已实现。工作区统一状态契约见 [ADR-0015](0015-统一工作区且不区分虚拟桌面.md)，代码符合性待验证。

```text
DesktopTools/
├─ src/                                  # React 前端

│  │  ├─ folder-portals/                 # 文件夹门户展示

│  │  └─ system-menu/                    # 桌面菜单和产品命令入口
│  ├─ bridge/                            # Tauri invoke/listen 调用封装
│  ├─ contracts/                         # 前端 DTO 与事件类型
│  ├─ shared/                            # 通用 UI、主题、格式化工具
│  └─ styles/                            # 全局主题与窗口基础样式
│
├─ src-tauri/
│  └─ src/                               # Rust 后端
│     ├─ main.rs                         # 进程入口
│     ├─ lib.rs                          # Tauri 应用装配
│     ├─ app/                            # 生命周期、运行时状态、退出流程

│     ├─ workspace/                      # 桌面布局领域
│     ├─ shell/                          # Windows Shell 操作代理
│     ├─ host/                           # 透明桌面宿主
│     ├─ persistence/                    # 布局快照与备份

│     ├─ recovery/                       # guardian、健康状态、重启恢复
│     ├─ platform/windows/               # Windows API 适配
│     ├─ contracts/                      # Rust 命令、事件、快照 DTO
│     └─ bin/guardian.rs                 # 独立恢复进程
│
├─ resources/                            # 图标、安装资源、静态资产
└─ docs/                                 # 领域文档、ADR、接口说明
```

前端只通过 `bridge/` 访问 Tauri 能力；Rust 通过 `commands/` 暴露受控命令；工作区、Shell、宿主、持久化、组件运行时和恢复模块按功能职责维护后端行为。

正式项目的功能数据流为：

```text
React 功能模块
  -> 类型化桥接层
  -> Tauri 命令与事件
  -> 应用命令边界
  -> 工作区 / Shell / 持久化 / 组件运行时
  -> Windows 平台适配器
  -> Explorer / WebView2 / 文件系统
  -> 不可变快照与事实事件
  -> React 功能模块
```

## 用户故事

1. 作为用户，我希望 Desktop Tools 呈现完整的桌面项目集合，以便在同一工作区整理 Windows 桌面。
2. 作为多显示器用户，我希望每台显示器拥有独立的透明桌面表面，使各屏的壁纸和任务栏工作区保持正确。
3. 作为调整显示缩放的用户，我希望每个宿主采用目标显示器的 DPI 和 WebView2 栅格化比例，使内容与输入坐标保持一致。
4. 作为桌面用户，我希望图标、名称和系统图像来自 Windows Shell，使显示的项目与系统命名空间一致。
5. 作为项目暂时不可用的用户，我希望保留项目引用和布局归属，以便 Windows 再次解析该项目后恢复原状。
6. 作为用户，我希望能够创建、移动、缩放、折叠、展开、锁定、排序和解散围栏，使桌面项目按我的工作方式组织。
7. 作为用户，我希望围栏归属只是逻辑关系，使项目在围栏之间移动时保持源位置不变。
8. 作为用户，我希望整个项目不区分 Windows 虚拟桌面，统一维护内容、布局和交互状态。
9. 作为切换虚拟桌面的用户，我希望工作区布局、选择和浏览状态保持不变。
10. 作为用户，我希望单选、多选、范围选择、键盘导航和焦点容器遵循 Windows 交互惯例，使工作区行为符合预期。
11. 作为拖动项目的用户，我希望获得预览、插入目标、自动滚动、成组移动和按 `Esc` 取消的能力，使布局修改可撤销且易于理解。
12. 作为将项目拖入围栏的用户，我希望逻辑归属更新与视觉落位作为同一事务提交，避免出现部分布局修改。
13. 作为使用桌面右键菜单的用户，我希望 Windows Shell 命令和 Desktop Tools 命令出现在对应目标的菜单中，使原生操作与产品操作共用一个交互入口。
14. 作为重命名、删除、复制、移动或还原项目的用户，我希望以 Windows Shell 返回结果确定最终状态，使工作区反映真实的文件系统与 Shell 操作结果。
15. 作为使用剪切和粘贴的用户，我希望剪切状态在整个工作区同步显示，使同一项目具有一致的可见传输状态。
16. 作为接收外部 Shell 变化的用户，我希望新建、删除、重命名和属性更新能同步到活动布局，使工作区跟随 Windows 的变化。
17. 作为用户，我希望支持自动快照、手动备份、当前 Schema 校验和还原，使布局在应用重启后保留，并能从配置错误中恢复。
18. 作为还原备份的用户，我希望还原统一工作区，不创建、删除或匹配 Windows 虚拟桌面。
19. 作为用户，我希望文件夹门户将目录内容呈现为可交互的工作区视图，以便从桌面表面访问大量项目。
20. 作为用户，我希望官方组件在工作区能力模型内运行，使扩展获得明确的宿主能力，并与宿主内部实现隔离。
21. 作为扩展作者，我希望获得稳定的组件契约与校验边界，使组件能独立于桌面宿主开发。
22. 作为用户，我希望 Desktop Tools 在渲染器重启期间保留最后可见帧和交互命中图，避免短暂的 WebView2 故障立即破坏桌面表面。
23. 作为用户，我希望 Explorer 重启后触发重新发现与附着，使桌面接管能从 Shell 进程生命周期变化中恢复。
24. 作为用户，我希望守护进程在启动失败、正常退出、`Ctrl+C` 或主进程崩溃后恢复 Explorer 可见性，使桌面接管始终具备恢复路径。
25. 作为用户，我希望当前 Windows 10 22H2 平台提供里程碑 1 的完整行为，使实现与验收遵循同一份可观察的产品契约。
26. 作为应用维护者，我希望前端呈现、桥接代码、领域规则、Shell 适配器和平台代码各有独立的职责边界，使功能演进不会将实现细节泄漏到其他层。
27. 作为应用维护者，我希望序列化命令、事件和快照契约明确，使前后端变化能在进程边界上审查。
28. 作为应用维护者，我希望当前契约测试、事实文档和 Windows 证据矩阵共同作为验收基线，使实现与已确认的桌面层行为保持一致。

## 实现决策

- 产品是一个 Tauri 桌面应用，由 React 前端、Rust 主进程和独立 Rust 守护进程可执行文件组成。
- 前端按产品能力组织：工作区表面、桌面项目、围栏、文件夹门户、组件、设置和系统菜单。
- 前端桥接层是功能代码调用原生能力的唯一入口，负责命令调用、事件订阅、请求组装、响应解码和前端契约类型。
- 前端状态分为渲染状态、交互状态和视图模型转换；领域规则、Shell 事实和持久化决策仍由后端负责。
- 后端命令边界校验序列化输入、调用功能模块，并发布不可变快照或事实事件。
- 工作区领域负责自有布局、围栏归属、选择集合、焦点容器、拖动事务、排序、滚动和布局撤销历史。
- Shell 适配器负责桌面命名空间枚举、稳定的 Shell 项目引用、系统图像、Shell 能力、原生上下文菜单、剪贴板操作、OLE 拖放和变化通知。
- Shell 适配器通过专用 STA 操作代理运行。窗口宿主线程持有自身的 HWND、WebView2 控制器、命中测试注册和 OLE 投放目标生命周期。
- 宿主运行时为每台显示器维护一个 `HostContext`，记录物理工作区、目标 DPI、有效栅格化比例、实际 HWND 状态、WebView2 控制器状态、可见性、层级和当前交互命中图。
- 宿主运行时在桌面接管前准备全部宿主。在命令通道可用的运行路径中，guardian 就绪且每台宿主页面、系统图像和命中图就绪后自动提交接管。像素与输入探针用于诊断，不作为自动提交门槛，避免空桌面或不可见像素采样阻塞启动；真实像素、壁纸透明和交互仍须实机验收，不能用提交日志替代。
- 显示器拓扑、工作区、DPI 或 Explorer 宿主变化触发宿主协调。仅 DPI 布局变化时保持现有接管状态；`Win+D` 引起同一 Explorer 视图的父窗口迁移时，重新附着现有 HWND 并恢复命中与显示，保留 WebView、OLE 注册及就绪状态。只有 Explorer 视图或列表身份替换才完整重建；重建在 UI 线程执行前重新发现当前 Shell 父窗口，旧 HWND 的迟到门槛和提交结果不覆盖新宿主状态。
- 持久化模块负责版本化 JSON 快照、原子写入、手动备份、当前 Schema 校验、读取校验、还原事务。
- 组件运行时负责组件清单、注册、能力声明、生命周期、组件状态持久化和面向宿主的事件。公开组件 SDK 留待后续里程碑交付。
- 恢复模块负责守护进程登记、健康状态阶段、渲染器重启协调、Explorer 重新发现、接管回滚和恢复状态报告。
- Windows 平台适配器封装 Win32、WebView2、显示器、DPI、Shell 兼容、键盘、菜单和 OLE 实现细节。
- 契约在序列化命令、事件和快照边界进行版本管理。前端 DTO 与 Rust DTO 使用一致的名称和字段语义；传输变更需要兼容性审查。
- Shell 事实与 Desktop Tools 布局事实保持分离。布局保存稳定项目引用和呈现状态；Shell 提供当前命名空间事实与操作结果。
- 布局修改形成显式事务。失败、取消或未改变状态的操作不产生撤销记录；成功的用户操作形成一个可逆布局单元。
- 支持补偿的 Shell 操作先记录已确认的原生结果，再创建可逆操作记录。永久删除不属于可逆操作集合。
- 功能演进保持 Shell 身份与 STA 操作代理、工作区领域与快照、宿主运行时、完整交互与 Shell 操作和组件契约之间的职责边界。
- 当前开发版本保留右侧平台与测试面板，提供接管状态、渲染器重载和显式退出控件。

## 测试决策

正式 Windows 桌面项目只输出 Rust `lib`，由主程序与 guardian 两个二进制消费；当前没有对外 C ABI 库或移动端入口，因而不生成 `cdylib`、`staticlib`。若以后出现真实外部链接或移动端需求，再单独确认发行边界。

开发与测试配置使用 `debug = 1`，保留基本函数和行号定位，减少调试产物及构建开销；这不等同于完整变量与类型调试。需要完整调试信息时可对单次 Cargo 调用覆盖 `CARGO_PROFILE_DEV_DEBUG=2` 或 `CARGO_PROFILE_TEST_DEBUG=2`，该覆盖会改变构建缓存。release 配置、MSVC 链接器和现有 crate 边界不变。

- 测试在最高可用边界断言外部可观察行为。主要测试边界是 React 桥接层与 Rust 命令处理函数之间的类型化 Tauri 命令与事件边界。
- 契约测试覆盖命令校验、事件载荷结构、不可变快照发布、错误映射和生命周期事件顺序。
- 工作区测试覆盖围栏归属、选择与焦点规则、拖动事务提交与取消、排序、切换虚拟桌面时保持工作区状态、快照还原和撤销时间线行为。
- Shell 测试通过适配器层替身覆盖稳定身份协调、重命名与删除及属性变化处理、操作结果映射、菜单能力选择、剪贴板状态和 OLE 传输结果。
- 宿主测试覆盖显示器协调、DPI 变化、WebView2 边界与栅格化配置、命中图发布、接管门槛、层级、Explorer 重新附着和恢复状态转换。
- 持久化测试覆盖快照原子写入、当前 Schema 校验、损坏或更高版本备份、还原回滚。
- 恢复测试覆盖守护进程握手、正常关闭、`Ctrl+C`、主进程崩溃、Explorer 重启、渲染器重启和宿主适配器失败。
- 前端测试覆盖视图模型映射、交互状态转换、命令分发、事件订阅和无障碍渲染状态。
- Windows 验收测试覆盖当前 Windows 10 22H2 平台、单显示器与多显示器、混合 DPI、锁定与解锁、睡眠与恢复、虚拟桌面切换、`Win+D`、Explorer 重启、正常退出和崩溃恢复。
- 测试依据包括当前 Rust 单元测试、前端测试、探针日志、Windows 证据矩阵和现有 ADR 验收边界。运行截图与日志仍是桌面层验收的一部分。
- 静态验证包括 Rust 格式化、Rust 测试、将警告视为错误的 Clippy 检查、前端类型检查、前端代码规范检查、前端测试、构建验证和 `git diff --check`。

## 已确认的设置与菜单需求

二级菜单对应图标属于已确认需求，图标覆盖与视觉方案仍待核验。设置的“性能”分类已提供“有应用全屏、最大化时暂停刷新”和“有应用获取焦点时暂停刷新”两个开关，默认关闭；覆盖策略逐屏判定，焦点策略作用于全部桌面，同时开启时取并集。暂停范围和恢复边界遵循本 ADR 的发布运行边界及订阅生命周期决策，不将开关已实现等同于所有消费者已通过恢复验收。

## 补充说明

### 已落实的架构深化

- 前端 `WorkspaceSurface` 集中逐屏展示、显示器命令路由和 Shell 结果呈现，`App` 只负责页面装配。展示投影不回写权威选择和持久归属，跨屏拖动仍接收完整工作区快照。
- `commands/workspace_menu.rs` 集中菜单可用项、DPI 坐标和产品选择解释。只接受当前菜单启用项的编号，动态编号映射基于菜单打开时的布局；Shell 动词和原生菜单仍经 Shell STA 执行。
- `WorkspaceEnvironment` 将同次观察的项目引用、名称、显示器、导入归属和精确重命名送入布局协调。名称缓存与布局在保存成功后共同提交；保存失败保持原状态。观察值不承诺跨运行时原子采集。
- 两种 transport 的业务编排共用各命令模块的 `execute_*` 实现，解码和序列化留在入口，不引入通用命令框架。事件错误沿用各领域错误契约；已完成的状态提交不因发布失败自动回滚，调用方应重新读取权威状态，避免盲目重试非幂等操作。
- 初始同步与恢复补读使用不广播事件的读取入口，组件使用 `get_current_component_runtime_snapshot`，避免只读同步重复触发广播。宿主发布失败保留日志处理策略。
- 系统强调色监听在退出时显式解除，支持重复清理并保留 Tauri 托管对象，避免移除对象导致已借用引用失效。

选择上述职责收拢是为了集中调用方需要共同遵守的规则；只移动文件或包装参数不能替代行为集中。实现提交、历史自动检查和未完成的实机验收见[架构深化验证记录](../validation/架构深化验证记录.md)。

该深化方案延续本 ADR 的职责划分。`WorkspaceState` 的文件长度不作为拆分依据；优先减少调用方承担的事实组合、路由和重复业务编排。

本架构的关键前提是继续以 Tauri 2、WebView2、独立 Rust 守护进程和已验证的原生窗口式宿主作为产品基础。调整这一基础会同时影响宿主、桥接、恢复和平台边界。

架构保留已批准的领域术语：桌面内容工作区、桌面接管、透明桌面宿主、交互命中区、交互命中图、Shell 操作代理、自有布局、围栏、文件夹门户、组件和组件 SDK。

本规格使用 `ready-for-agent` 分流标签，已具备进入实现工作的条件。每个实现阶段都应保持应用结构可用，并通过当前契约测试与 Windows 验收证据核对行为。
