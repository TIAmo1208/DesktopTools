# 频谱设备热插拔采用端点通知

设置页的设备列表与频谱采集的目标设备改由 Windows Core Audio 端点通知驱动：进程内按需运行一条监听线程，注册 `IMMNotificationClient`，去抖后重新枚举设备；列表真正变化时向后端事件 `audio-devices-changed` 投递最新设备列表，并推进设备代数让采集线程重建。设置面板与采集线程各持有一个监听开关，全部关闭后注销回调并退出线程；采集线程不再每 2 秒自查设备，只保留 10 秒兜底检查。

## 已确认决策

设置面板打开期间与采集运行期间，设备变化以端点通知为准；两者都不在轮询设备列表。通知回调只向通道发送信号，枚举、比较与事件投递都在监听线程完成，避免在 COM 回调线程上做重活。采集线程按设备代数重建，不再自行比较设备标识。

设备规则保持不变：保存的设备存在时始终使用；设备消失时回退系统默认但保留保存值；未保存设备（跟随系统默认）时随系统默认切换。新设备接入只有在它成为系统默认或正是保存设备时才会切换采集目标。

## 原因与职责边界

原实现只在打开「音乐控制」面板时读一次设备列表，插拔后必须重新进入面板才刷新；采集线程每 2 秒自查一次，拔出到回退最多滞后 2 秒，并且自查本身也构成持续轮询。实测插拔后列表与采集切换均在 0.3 秒内完成，前端不再需要定时器，采集线程也去掉了周期自查。

监听线程只在有消费者时存在，设置窗口销毁时复位设置页开关。监听线程不持有采集状态，采集线程也不注册回调；两侧只通过设备代数与事件名解耦。事件只在列表真正变化时投递，默认设备切换会改变列表中的系统默认标记，因此同样会触发一次投递。

## 待验证假设

- 保存指定设备（非「跟随系统默认」）时，设备消失与回归的端到端路径尚未复测；设备解析函数未改动。
- 端点刚变化时首次重建偶尔返回 `RPC_E_CHANGED_MODE`，退避重试可恢复；该错误与调用线程套间无关，尚未在不同声卡驱动上复核。
- 连续 20 次拔插的句柄与线程趋势、蓝牙等延迟枚举设备未验证。
