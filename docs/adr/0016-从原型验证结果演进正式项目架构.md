# 从原型验证结果演进正式项目架构

## 问题说明

Desktop Tools 已通过 `native-windowed-adapter` 原型验证透明桌面宿主、逐屏 WebView2、混合 DPI、桌面接管、交互命中、围栏操作、Explorer 重启和 guardian 恢复等关键行为。原型代码把宿主、Shell 访问、布局状态、前端呈现和恢复流程集中在验证路径中，正式项目需要一套按功能职责拆分的结构承接这些已确认行为。

当前架构需要同时满足以下事实：

- Desktop Tools 拥有桌面项目的呈现与交互，Windows Explorer 提供桌面命名空间、Shell 操作和恢复兜底。
- React/WebView2 负责视觉状态和交互意图，Rust 负责领域规则、Windows 能力和应用生命周期。
- Shell 项目身份与 Desktop Tools 自有布局分别维护，Shell 返回结果作为文件操作事实来源。
- 每台显示器拥有独立透明桌面宿主，宿主需要维护物理工作区、DPI、WebView2 栅格化比例和交互命中图。
- 启动失败、正常退出、Explorer 重启、主进程崩溃和宿主失效都需要进入统一恢复契约。

## 解决方案

正式项目采用单应用双边界架构：

1. React 前端按产品功能组织工作区、桌面项目、围栏、文件夹门户、组件和设置，并通过类型化桥接层表达命令与事件。
2. Rust 后端按桌面宿主、Shell、工作区领域、持久化、组件运行时和恢复组织功能模块。
3. Tauri 命令与事件边界作为前后端最高层测试边界，承担参数校验、快照发布和结果回传；平台实现留在 Rust 的 Windows 适配层。
4. Shell 适配器在专用 STA 操作代理中运行，宿主线程持有对应 HWND 和 OLE 生命周期。
5. 独立 Rust 守护进程 负责接管前的状态登记、运行期间观察和异常恢复；业务状态、布局和 Shell 操作结果由主进程持有。
6. 原型目录保持冻结，原型中的宿主行为、状态门槛和日志事件作为正式实现的迁移参考。

## 当前文件结构

```text
DesktopTools/
├─ src/                                  # React 前端
│  ├─ app/                               # 应用启动、根布局、全局状态装配
│  ├─ features/
│  │  ├─ workspace/                      # 桌面内容工作区
│  │  │  ├─ surface/                     # 透明桌面表面、显示器工作区呈现
│  │  │  ├─ interaction/                 # 命中、焦点、选择、框选、拖动
│  │  │  ├─ state/                       # 前端交互状态与临时编辑状态
│  │  │  └─ view-models/                 # 后端数据到展示模型的转换
│  │  ├─ desktop-items/                  # 桌面项目图标、名称、选中、打开
│  │  ├─ fences/                         # 围栏标题、成员、滚动、折叠、布局
│  │  ├─ folder-portals/                 # 文件夹门户展示
│  │  ├─ components/                     # Desktop Tools 组件展示
│  │  ├─ settings/                       # 设置界面
│  │  └─ system-menu/                    # 桌面菜单和产品命令入口
│  ├─ bridge/                            # Tauri invoke/listen 调用封装
│  ├─ contracts/                         # 前端 DTO 与事件类型
│  ├─ shared/                            # 通用 UI、主题、格式化工具
│  └─ styles/                            # 全局主题与窗口基础样式
│
├─ src-tauri/
│  └─ src/                               # Rust 后端
│     ├─ main.rs                         # 进程入口
│     ├─ lib.rs                          # Tauri 应用装配
│     ├─ app/                            # 生命周期、运行时状态、退出流程
│     ├─ commands/                       # 前端命令边界
│     ├─ workspace/                      # 桌面布局领域
│     ├─ shell/                          # Windows Shell 操作代理
│     ├─ host/                           # 透明桌面宿主
│     ├─ persistence/                    # 布局快照与备份
│     ├─ component_runtime/              # 组件清单、能力和运行时
│     ├─ recovery/                       # guardian、健康状态、重启恢复
│     ├─ platform/windows/               # Windows API 适配
│     ├─ contracts/                      # Rust 命令、事件、快照 DTO
│     └─ bin/guardian.rs                 # 独立恢复进程
│
├─ resources/                            # 图标、安装资源、静态资产
├─ docs/                                 # 领域文档、ADR、接口说明
├─ .scratch/                             # 需求、规格、工单、验证证据
└─ prototypes/tauri-desktop-host/       # 冻结的宿主行为参考
```

前端只通过 `bridge/` 访问 Tauri 能力；Rust 通过 `commands/` 暴露受控命令；工作区、Shell、宿主、持久化、组件运行时和恢复模块按功能职责维护后端行为；`prototypes/tauri-desktop-host` 继续作为冻结的宿主行为参考。

正式项目的功能数据流为：

```text
React 功能模块
  -> 类型化桥接层
  -> Tauri 命令与事件
  -> 应用命令边界
  -> 工作区 / Shell / 持久化 / 组件运行时
  -> Windows 平台适配器
  -> Explorer / WebView2 / 文件系统
  -> 不可变快照与事实事件
  -> React 功能模块
```

## 用户故事

1. 作为用户，我希望 Desktop Tools 呈现完整的桌面项目集合，以便在同一工作区整理 Windows 桌面。
2. 作为多显示器用户，我希望每台显示器拥有独立的透明桌面表面，使各屏的壁纸和任务栏工作区保持正确。
3. 作为调整显示缩放的用户，我希望每个宿主采用目标显示器的 DPI 和 WebView2 栅格化比例，使内容与输入坐标保持一致。
4. 作为桌面用户，我希望图标、名称和系统图像来自 Windows Shell，使显示的项目与系统命名空间一致。
5. 作为项目暂时不可用的用户，我希望保留项目引用和布局归属，以便 Windows 再次解析该项目后恢复原状。
6. 作为用户，我希望能够创建、移动、缩放、折叠、展开、锁定、排序和解散围栏，使桌面项目按我的工作方式组织。
7. 作为用户，我希望围栏归属只是逻辑关系，使项目在围栏之间移动时保持源位置不变。
8. 作为用户，我希望每个 Windows 虚拟桌面拥有独立布局，使同一项目集合在不同桌面中采用各自的围栏和组件排列。
9. 作为切换虚拟桌面的用户，我希望活动布局、选择集合、焦点和拖动状态协调切换，避免遗留旧桌面的交互状态。
10. 作为用户，我希望单选、多选、范围选择、键盘导航和焦点容器遵循 Windows 交互惯例，使工作区行为符合预期。
11. 作为拖动项目的用户，我希望获得预览、插入目标、自动滚动、成组移动和按 `Esc` 取消的能力，使布局修改可撤销且易于理解。
12. 作为将项目拖入围栏的用户，我希望逻辑归属更新与视觉落位作为同一事务提交，避免出现部分布局修改。
13. 作为使用桌面右键菜单的用户，我希望 Windows Shell 命令和 Desktop Tools 命令出现在对应目标的菜单中，使原生操作与产品操作共用一个交互入口。
14. 作为重命名、删除、复制、移动或还原项目的用户，我希望以 Windows Shell 返回结果确定最终状态，使工作区反映真实的文件系统与 Shell 操作结果。
15. 作为使用剪切和粘贴的用户，我希望剪切状态在各活动虚拟桌面中同步显示，使同一项目具有一致的可见传输状态。
16. 作为接收外部 Shell 变化的用户，我希望新建、删除、重命名和属性更新能同步到活动布局，使工作区跟随 Windows 的变化。
17. 作为用户，我希望支持自动快照、手动备份、Schema 迁移和还原，使布局在应用重启后保留，并能从配置错误中恢复。
18. 作为还原备份的用户，我希望保留当前 Windows 虚拟桌面，并按稳定身份还原匹配的布局，避免还原操作意外改变当前桌面上下文。
19. 作为用户，我希望文件夹门户将目录内容呈现为可交互的工作区视图，以便从桌面表面访问大量项目。
20. 作为用户，我希望官方组件在工作区能力模型内运行，使扩展获得明确的宿主能力，并与宿主内部实现隔离。
21. 作为扩展作者，我希望获得稳定的组件契约与校验边界，使组件能独立于桌面宿主开发。
22. 作为用户，我希望 Desktop Tools 在渲染器重启期间保留最后可见帧和交互命中图，避免短暂的 WebView2 故障立即破坏桌面表面。
23. 作为用户，我希望 Explorer 重启后触发重新发现与附着，使桌面接管能从 Shell 进程生命周期变化中恢复。
24. 作为用户，我希望守护进程在启动失败、正常退出、`Ctrl+C` 或主进程崩溃后恢复 Explorer 可见性，使桌面接管始终具备恢复路径。
25. 作为用户，我希望当前 Windows 10 22H2 平台提供里程碑 1 的完整行为，使实现与验收遵循同一份可观察的产品契约。
26. 作为应用维护者，我希望前端呈现、桥接代码、领域规则、Shell 适配器和平台代码各有独立的职责边界，使功能演进不会将实现细节泄漏到其他层。
27. 作为应用维护者，我希望序列化命令、事件和快照契约明确，使前后端变化能在进程边界上审查。
28. 作为应用维护者，我希望保留原型行为作为验收基线，使正式实现能与已验证的桌面层行为对比。

## 实现决策

- 产品是一个 Tauri 桌面应用，由 React 前端、Rust 主进程和独立 Rust 守护进程可执行文件组成。
- 前端按产品能力组织：工作区表面、桌面项目、围栏、文件夹门户、组件、设置和系统菜单。
- 前端桥接层是功能代码调用原生能力的唯一入口，负责命令调用、事件订阅、请求组装、响应解码和前端契约类型。
- 前端状态分为渲染状态、交互状态和视图模型转换；领域规则、Shell 事实和持久化决策仍由后端负责。
- 后端命令边界校验序列化输入、调用功能模块，并发布不可变快照或事实事件。
- 工作区领域负责虚拟桌面布局、围栏归属、选择集合、焦点容器、拖动事务、排序、滚动和布局撤销历史。
- Shell 适配器负责桌面命名空间枚举、稳定的 Shell 项目引用、系统图像、Shell 能力、原生上下文菜单、剪贴板操作、OLE 拖放和变化通知。
- Shell 适配器通过专用 STA 操作代理运行。窗口宿主线程持有自身的 HWND、WebView2 控制器、命中测试注册和 OLE 投放目标生命周期。
- 宿主运行时为每台显示器维护一个 `HostContext`，记录物理工作区、目标 DPI、有效栅格化比例、实际 HWND 状态、WebView2 控制器状态、可见性、层级和当前交互命中图。
- 宿主运行时在桌面接管前准备全部宿主。页面就绪、图标探针、像素探针、命中图发布、守护进程就绪和命令通道就绪全部通过后，自动修改 Explorer 图标可见性；正常启动不依赖人工输入探针，也不使用启动后自动退出机制。
- 显示器拓扑、工作区、DPI 或 Explorer 宿主变化触发宿主协调。仅 DPI 布局变化时保持现有接管状态；Explorer 身份变化时执行完整的重新附着流程。
- 持久化模块负责版本化 JSON 快照、原子写入、手动备份、Schema 迁移、读取校验、还原事务和布局归档。
- 组件运行时负责组件清单、注册、能力声明、生命周期、组件状态持久化和面向宿主的事件。公开组件 SDK 留待后续里程碑交付。
- 恢复模块负责守护进程登记、健康状态阶段、渲染器重启协调、Explorer 重新发现、接管回滚和恢复状态报告。
- Windows 平台适配器封装 Win32、WebView2、显示器、DPI、Shell 兼容、虚拟桌面、键盘、菜单和 OLE 实现细节。
- 契约在序列化命令、事件和快照边界进行版本管理。前端 DTO 与 Rust DTO 使用一致的名称和字段语义；传输变更需要兼容性审查。
- Shell 事实与 Desktop Tools 布局事实保持分离。布局保存稳定项目引用和呈现状态；Shell 提供当前命名空间事实与操作结果。
- 布局修改形成显式事务。失败、取消或未改变状态的操作不产生撤销记录；成功的用户操作形成一个可逆布局单元。
- 支持补偿的 Shell 操作先记录已确认的原生结果，再创建可逆操作记录。永久删除不属于可逆操作集合。
- 正式迁移依次推进 Shell 身份与 STA 操作代理、工作区领域与快照、宿主运行时、完整交互与 Shell 操作、虚拟桌面协调和组件契约。
- 原型保持为冻结的行为参考。正式模块承接已验证机制；当前开发版本保留右侧平台与测试面板，提供接管状态、渲染器重载和显式退出控件。

## 测试决策

- 测试在最高可用边界断言外部可观察行为。主要测试边界是 React 桥接层与 Rust 命令处理函数之间的类型化 Tauri 命令与事件边界。
- 契约测试覆盖命令校验、事件载荷结构、不可变快照发布、错误映射和生命周期事件顺序。
- 工作区测试覆盖围栏归属、选择与焦点规则、拖动事务提交与取消、排序、虚拟桌面布局隔离、快照还原和撤销时间线行为。
- Shell 测试通过适配器层替身覆盖稳定身份协调、重命名与删除及属性变化处理、操作结果映射、菜单能力选择、剪贴板状态和 OLE 传输结果。
- 宿主测试覆盖显示器协调、DPI 变化、WebView2 边界与栅格化配置、命中图发布、接管门槛、层级、Explorer 重新附着和恢复状态转换。
- 持久化测试覆盖快照原子写入、Schema 迁移、损坏或更高版本备份、还原回滚和布局归档保留。
- 恢复测试覆盖守护进程握手、正常关闭、`Ctrl+C`、主进程崩溃、Explorer 重启、渲染器重启和宿主适配器失败。
- 前端测试覆盖视图模型映射、交互状态转换、命令分发、事件订阅和无障碍渲染状态。
- Windows 验收测试覆盖当前 Windows 10 22H2 平台、单显示器与多显示器、混合 DPI、锁定与解锁、睡眠与恢复、虚拟桌面切换、`Win+D`、Explorer 重启、正常退出和崩溃恢复。
- 测试参考来自原型的 Rust 单元测试、前端自检、探针日志、Windows 证据矩阵和现有 ADR 验收边界。运行截图与日志仍是桌面层验收的一部分。
- 静态验证包括 Rust 格式化、Rust 测试、将警告视为错误的 Clippy 检查、前端类型检查、前端代码规范检查、前端测试、构建验证和 `git diff --check`。

## 范围之外

- 第三方组件分发、公开组件 SDK 打包、能力市场和组件沙箱策略。
- 文件夹门户搜索、跨目录批量工作流，以及超出里程碑 1 交互契约的高级 Shell 工作流。
- macOS 和 Linux 的桌面接管、Shell 集成、原生菜单和平台验收。
- 替代 Windows 任务栏、开始菜单、应用切换或通用窗口管理。
- 在 React 或工作区领域中重新实现 Windows Shell 文件操作语义。
- 除保留的右侧平台与测试面板外，原型专用的静态示例数据和仅用于探针的命令通道。
- 后续里程碑负责的安装程序签名、更新渠道、发行品牌和分发基础设施。

## 补充说明

本架构的关键前提是继续以 Tauri 2、WebView2、独立 Rust 守护进程和已验证的原生窗口式宿主作为产品基础。调整这一基础会同时影响宿主、桥接、恢复和平台边界。

架构保留已批准的领域术语：桌面内容工作区、桌面接管、透明桌面宿主、交互命中区、交互命中图、Shell 操作代理、自有布局、虚拟桌面布局、围栏、文件夹门户、组件和组件 SDK。

本规格使用 `ready-for-agent` 分流标签，已具备进入实现工作的条件。每个实现阶段都应保持应用结构可用，并保留原型用于行为对比。
