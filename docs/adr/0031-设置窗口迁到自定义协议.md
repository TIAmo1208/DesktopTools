# 设置窗口迁到自定义协议

插件入口脚本统一用 `await import("/plugins/<相对路径>")` 加载。`script-src 'self'` 只放行同源模块，因此设置窗口必须自己提供 `/plugins/` 路由。

本决策推翻此前「设置窗口用 `window.eval` 执行脚本」的口径：不再注册 `load_plugin_script`，也不再在宿主侧执行脚本正文。

## 决策

设置窗口仍由托盘按需创建。尺寸、装饰、关闭即销毁、重开、主题和托盘显隐继续使用 `tauri.conf.json` 里 `main` 窗口的配置与现有 `on_window_event`。只把页面地址改为 `http://desktop-tools-settings.localhost/`。

应用启动时注册自定义协议 `desktop-tools-settings`。Tauri 创建 WebView 时由 wry 的 `with_asynchronous_custom_protocol` 挂上该协议。请求处理复用逐屏宿主的 `handle_protocol_request`：内嵌页面与资源、`/plugins/` 下的 `.js` 与 `.css`、`/__desktop_tools_invoke/` 命令。路径校验、内容类型和内容安全策略头都沿用这条函数，不另写一套。

逐屏宿主继续使用各自的 `desktop-tools-host-<序号>`，不改为这个协议。不修改 `tauri.conf.json` 的 CSP。

`/__desktop_tools_invoke/` 在阻塞池执行，避免命令等待 Shell STA 时卡住 WebView UI 线程。页面和插件资产在协议线程直接返回。

### IPC

查证锁定版本 Tauri 2.11.5、tauri-runtime-wry 2.11.4、wry 0.55.1 的源码，不改设置页的命令与事件通道：

- Windows 上初始化脚本通过 `AddScriptToExecuteOnDocumentCreated` 注入，不看页面来源。`window.__TAURI_INTERNALS__` 与 `window.ipc.postMessage` 在文档创建时就存在。
- `invoke` 先请求 `http://ipc.localhost/...`。`ipc` 是同一个 WebView 上的另一个自定义协议。该响应带 `Access-Control-Allow-Origin: *`。现有 CSP 的 `connect-src` 已包含 `ipc:` 与 `http://ipc.localhost`。这次请求失败时，同一段初始化脚本改走 `postMessage`。
- 已注册协议的来源 `http://<协议名>.localhost` 被 Tauri 的 `is_local_url` 视为本地来源，访问控制仍是 `Origin::Local`。能力按窗口标签 `main` 匹配，不按原来的资产来源匹配。
- `listen` 走同一套 `invoke`。事件投递由宿主执行初始化脚本注册的回调，不依赖页面来源。

因此设置窗口不改用 `__DESKTOP_TOOLS_NATIVE__`。上述版本的行为若变化，再单独立项；不在这条协议上做静默降级。

同源 `import("/plugins/<相对路径>")` 受 `script-src 'self'` 约束，不需要 `unsafe-inline` 或 `unsafe-eval`。插件响应不另加 CSP 头。

## 后果

- 设置窗口与插件脚本同源，资产拒绝规则与逐屏宿主相同。
- 开发模式没有内嵌资源时，页面从 `frontendDist` 读取，不走 Vite 开发服务器，设置窗口没有热更新。该模式下资产解析不附带 CSP 头；正式构建仍附带配置里的 CSP。
- 前端入口模块使用同源 `import` 加载，不调用 `load_plugin_script`。

## 待验证假设

- 上述 IPC 结论来自锁定版本的源码路径，尚未在本决策撰写时用 WebView2 打开设置窗口复测 `invoke` 与 `listen`。
