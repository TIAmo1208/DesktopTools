# 插件 loopback 通道

## 背景

插件要读的数据源（例如本机 AstrBot）只提供本机 HTTP 数据，而这些数据既不在宿主已知能力里，也不能由页面直连：页面 CSP 是 `connect-src 'self'`，服务端没有 CORS 头，凭据也不允许进入页面。

[AstrBot 状态采集链路](0036-AstrBot状态采集链路.md) 已决定采集在 AstrBot 进程内完成，Desktop Tools 侧只是接收方。只做 AstrBot 专用能力会把「解析、缓存、去重」写进宿主，每加一个数据源就要再开一条能力，两侧都要改代码。

## 决策

宿主只提供通用传输，数据含义归插件。

### 能力与声明

- 新增宿主能力 `loopback-channel`，写入插件槽能力白名单，与 `read-host-time`、`read-current-media`、`probe-service-status` 并存。
- 插件槽仍**只放行单元素声明**：清单 `required_capabilities` 一次声明其中一个能力，组合声明整份清单不注册。需要探活又想开通道的插件，按需在两者中择一并自行取舍。
- AstrBot 插件只声明 `loopback-channel`，不再声明 `probe-service-status`；六类格子全部走通道，不保留探活旧路径。

### 通道模型

一条通道是一个「本机端点 + 方向」的句柄，由插件在自己所在的实例上注册：

| `mode` | 含义 | 端点字段 |
| --- | --- | --- |
| `listen` | 宿主在 `127.0.0.1:<port>` 监听，接住对端推送 | `port`（必填，`1`–`65535`），不接受 `baseUrl` |
| `request` | 宿主向 `baseUrl` 发请求 | `baseUrl`（必填），不接受 `port` |

- `baseUrl` 只接受 `http://127.0.0.1:<port>` 或 `http://localhost:<port>`，统一归一为 `http://127.0.0.1:<port>`；其它主机、`https`、带路径的基址一律拒绝。
- 宿主只绑本机 IPv4 回环地址，不接受 `0.0.0.0`、局域网地址或远端地址。
- 端口被占用时注册失败并给 `loopback-port-in-use`，宿主不抢占端口、不改用其它端口。
- 通道属于实例：实例被移除、插件被卸载或页面销毁时释放端口并丢弃缓冲。

### 命令

能力只从能力通道交付，插件按 `instanceId` 调用；平铺原生命令表不因插件声明而放入任何通道入口的额外权限，三条命令同样只对已授权 `loopback-channel` 的实例生效。

| 命令 | 入参 | 返回 |
| --- | --- | --- |
| `register_loopback_channel` | `instanceId`、`channelId`、`mode`（`listen` / `request`）、`port` 或 `baseUrl`、可选 `credentialRef`、可选 `headerName` | 句柄 `{ channelId, mode, port, baseUrl, registeredAt }` |
| `read_loopback_channel` | `instanceId`、`channelId`、可选 `afterSequence` | 原始请求数组 |
| `request_loopback` | `instanceId`、`channelId`、`method`、`path`、可选 `body` | 原始响应 `{ status, headers, body }` |

- 句柄里 `port` 与 `baseUrl` 互斥：`listen` 给端口、`request` 给基址，另一项为 `null`。句柄不进入工作区快照、不落盘，页面重载后需重新注册。
- `channelId` 由插件声明，按组件标识同一字符集校验（小写字母、数字、`.`、`-`，长度不超过 128）且必须校验通过，实例内唯一；重复注册同名通道以最后一次为准，旧端口与缓冲一并释放，且同名的这一次不占通道额度。
- 入站请求条目是原始数据：`sequence`（宿主递增，从 1 起）、`receivedAt`（Unix 秒）、`method`、`path`、`headers`（数组，保留重复与顺序）、`body`（UTF-8 文本）。宿主不解析 body、不改写字段、不校验业务结构。
- 只有 HTTP/1.1 单条请求、以 `Content-Length` 定长请求体；chunked 与管线化请求按无效请求处理。
- `read_loopback_channel` 返回后即消费：同一 `sequence` 不会再出现；传了 `afterSequence` 时只返回序号更大的条目。首次读取把该通道标记为已订阅，此后缓冲更新才发通知。
- `request_loopback` 返回原始响应，`status` 非 2xx 照常返回、由插件判断；只有传输层失败（连不上、超时、响应超限、通道方向不符）才返回命令错误。`method` 只接受 ASCII 字母数字与 `-`、`_`；`path` 必须以 `/` 开头、不含换行与 `#`、不以 `//` 开头。

### 通知

- 复用既有宿主事件 `component-host-event`，`kind` 为 `loopback-data:<channelId>`，事件结构不增加字段。
- 插件从 `kind` 解析出通道标识，再回来调用 `read_loopback_channel` 取数据；事件本身不携带请求内容。
- 投递条件按通道自身状态决定：该通道被读过一次后才发通知，之前只入缓冲。逐屏转发时，通道数据通知**不**依据该屏是否存在时间消费者（时间节拍事件仍按时间消费者过滤），否则没有订阅时间的插件在独立桌面宿主上收不到通知。

### 宿主缓冲的含义

宿主缓存的是**带 `sequence` 的原始请求缓冲**，不是解析后的业务快照：

- 每条通道最多 256 条、单条 `body` 上限 1 MiB、整体保留 300 秒；超限丢最旧的条目。
- 缓冲清理只按条数与时间，**不判断业务是否新鲜**；业务过期由插件自己定义（AstrBot 插件为接收 30 秒、显示 60 秒）。
- 缓冲随实例存活，不落盘。

### 凭据

- 通道注册时插件声明 `credentialRef`（Windows Credential Manager 的目标名）与 `headerName`；`headerName` 由插件声明，宿主不写死。只声明其一视为声明错误，注册失败。
- 头名按 HTTP token 字符集校验，挡住 CR/LF 注入。
- 宿主用 `CredReadW` 读通用凭据，读出后立即把系统缓冲区清零并释放；密钥只留在宿主内存里。
- 出站：`request_loopback` 自动带上该头。入站：校验该头，值用常量时间比较；失败回 `401`，请求不进入缓冲、不交给插件。
- 已校验的凭据头在交给插件前从头列表里移除，插件拿不到密钥明文；密钥不写日志、不进普通偏好、不进工作区快照。
- 未声明 `credentialRef` 的通道不做注入与校验，适合无鉴权的本机数据源。
- 凭据记录不存在或读取失败时，注册返回 `loopback-credential-unavailable`；插件据此进入未配对态，不再重复注册，等用户在设置页保存或清除共享凭据后再重试。凭据变更由插件设置里的配对版本计数传达：设置页写成功即递增，插件发现它变大就重新注册通道，不新增宿主命令。

### 硬限制与错误

- 只绑本机回环地址，端口与地址同上。
- 每个实例最多 2 条通道；超出时注册失败。
- 入站请求头总长上限 16 KiB、单条 `body` 上限 1 MiB，超限回 `413` 并计入丢弃；请求行或头格式无效回 `400` 并计入丢弃；被丢弃的入站请求不静默当成正常数据。
- 出站响应体上限 4 MiB，超限按传输失败返回。
- 结构化错误码：`loopback-port-in-use`、`loopback-address-invalid`、`loopback-channel-limit`、`loopback-credential-unavailable`、`loopback-channel-not-found`、`loopback-request-failed`，均附中文说明。
- 日志只记通道标识、方向、端口或地址与结果，不写请求与响应 `body`、不写凭据与鉴权头。

### 业务归插件

- AstrBot 的 8765 推送、8766 拉取与启停平台、`snapshot.schema.json` 的解析与校验、调用去重、过期判定，全部在插件内完成；宿主对这些一无所知。
- 插件用模块级单例缓存共享解析结果：同一插件的多个类型实例共用一条通道、一份快照、一个定时器，按 `instanceId` 去重。
- 平台启停走 `request_loopback` 的 `POST`，不另设写能力声明，通道 `mode=request` 即可承载。

### 类型级尺寸

- 扩展 [插件声明多种格子类型](0037-插件声明多种格子类型.md)：清单让每个类型声明默认尺寸与最小尺寸；未声明时沿用公共格子默认尺寸与公共最小尺寸。
- 清单写法：`[tiles]` 声明类型后，用独立的 `[tiles.size]` 节按类型键补充尺寸，每行 `类型键 = 默认宽x高` 或 `类型键 = 默认宽x高, 最小宽x高`，宽高是正整数 DIP，上限 `10000`，最小项可省略。
- 只接受 `[tiles]` 已声明的类型键；未知键、非法尺寸、重复行只记 WARN 并忽略该行，不拒绝整份清单。
- 下发到前端的清单里，每个类型带 `defaultSize` 与 `minimumSize`（未声明为 `null`）。
- 创建插件格子时用该类型的默认尺寸，未声明时用公共默认尺寸，且不低于该类型的有效下限；工作区创建命令按实例 `state.tileType` 再校验一次有效下限。
- 类型级尺寸只影响创建时的默认外框与该实例的有效下限，不改变外壳几何规则（`28 DIP` 标题轨道、`1 DIP` 边框与留白）与折叠尺寸。

### 外壳菜单注入

- 扩展 [插件来源与范围](0029-插件来源与范围.md) 的外壳 `context`，增加 `menu` 注册接口：插件在 `renderTile` 期间调用 `context.menu.register(items)`，返回一个清理函数。
- 每项是 `{ id, label, disabled?, description?, separatorBefore?, danger?, onSelect }`：`id` 在实例内唯一，`label` 是用户可见命令，`onSelect` 是点击回调；其余字段可选，分别表示置灰、禁用原因、与前一组用分隔线隔开、危险命令配色。
- 注册以最后一次为准：同一实例再次 `register` 会整体替换上一轮列表。缺 `id`、`label` 或 `onSelect` 的项被丢弃，重复 `id` 保留首项，都记 WARN。
- 菜单项归实例：清理函数与该实例最近一次 `renderTile` 返回的清理函数同一生命周期；实例卸载、重挂或重新渲染前都会撤下旧项。
- 实例不可渲染（脚本加载失败、插件停用）、未注册或注册项非法时不显示该项。
- 菜单项只能调用插件自己的逻辑，宿主不代为执行网络或文件操作。

## 原因与职责边界

宿主知道自己能做的事（本机回环上的收发、Credential Manager、事件）、插件知道自己数据的含义。把边界切在「原始 HTTP」上，新数据源不需要改宿主代码，AstrBot 的字段语义也不必进宿主。

这与既有三个能力「宿主归一化最小结构」的形态不同，是有意的边界变化：`loopback-channel` 的载荷是整份原始透传，宿主不做归一化裁剪、不校验业务 schema。代价是解析、缓存、去重搬到插件，每个新数据源各写一遍；宿主的保证只剩端口、凭据与传输。

## 后果

- 插件成为网络能力持有者：能指定本机端口与地址、能借宿主的凭据注入访问本机服务。能力门禁（清单声明 + 单元素白名单）成为唯一边界。
- [ADR-0029](0029-插件来源与范围.md) 的「作者受信」前提不变，但权重上升——通道能力把「作者代码在页内执行」的信任范围扩到本机网络。
- 宿主不再对插件数据做 schema 校验，坏数据、字段缺失与异常形态由插件兜底；格子显示什么完全取决于插件的解析质量。
- 解析、缓存、去重由宿主移到插件，同一份数据在多个类型实例间靠插件自行共享；插件写得不严谨就会多开端口或重复轮询，宿主不代为去重。
- 缓冲只按条数与时间清理，业务新鲜度判定归插件；同一份原始数据在不同插件里可能得到不同的过期结论，这是接受的设计。
- 端口是独占资源：同一台机器上同时运行两个声明同一端口的插件实例会注册失败；AstrBot 插件因此在 8765 被占用时退回只用 8766 拉取兜底。

## 待验证与待完成

- 入站推送与 `request_loopback` 的端到端时延、监听线程的接受节奏与高并发下的丢弃行为尚未在真实桌面对端上验收。
- 凭据缺失、对端 `401`、端口被抢占三类失败在格子上的呈现只由单元测试与假宿主覆盖，未做真机注入。
- `src/bridge/loopback.ts` 的订阅工厂目前只被契约测试使用，插件走自己的页面桥调用通道命令；是否保留该封装待定。
