# 浮岛音乐进度以系统媒体控制跳转

## 背景

浮岛展开音乐卡的进度条此前只显示播放位置，不能拖动。用户要求进度可控制，先确认系统接口能否完成媒体进度控制，能控制再接上控制接口。

Windows GSMTC（`GlobalSystemMediaTransportControlsSession`）提供 `IsPlaybackPositionEnabled`、`TryChangePlaybackPositionAsync` 与 `GetTimelineProperties()` 的 `MinSeekTime` / `MaxSeekTime`；当前依赖 `windows 0.61.3` 已暴露这些接口，不需要升级。播放器是否真的执行跳转由它自己决定，系统只给出能力位与可跳转区间。

## 决策

- Rust 侧新增 `seek_music_position(expected_session, position_ms)`，沿用既有媒体动作的共享门闩、专用 MTA 工作线程、4 秒内层期限与 5 秒调用等待：发送前重新获取当前会话并要求会话代次与实例都未变，重新校验 `IsPlaybackPositionEnabled`，按系统 `MinSeekTime` / `MaxSeekTime` 夹紧目标（负区间按 0 处理，量程缺失或反序时不夹上界），毫秒乘 `10_000` 换成 100ns ticks 且不溢出。`Ok(false)` 与 HRESULT 错误分开处理，超时只说明结果未确认，不重发跳转。
- 发送成功、失败与结果未确认都请求回读：立即一次，再在 150 / 400 / 900 毫秒各补一次有界回读，播放器迟更新的时间轴也能被读到。不订阅 `TimelinePropertiesChanged`：部分播放器（实测 QQ 音乐）以高频事件推进时间轴，订阅会把读取放大成事件触发的读取风暴，回读次数改为固定上限。跳转区间与时间轴在同一次读取里取回，不额外增加 COM 调用。
- 媒体快照增加 `canSeek` 与系统可跳转区间 `seekMinMs` / `seekMaxMs`。展开卡进度条的量程优先取系统区间，没有区间时退回时间轴时长，再退回歌词兜底量程。
- 可控性在渲染前按能力位决定：`canSeek` 为真才渲染滑块，否则渲染同一套视觉的静态进度条——不提供悬停反馈、不显示手型、不发跳转。只读与可拖共用轨道 `3`、圆点 `10`、命中高度 `16`，区别只在交互反馈，避免把不可控控件画成可控。能力位为真但没有可能量程时同样只读。
- 播放器可能「接受调用但不改位置」（实测 QQ 音乐：`TryChangePlaybackPositionAsync` 返回 true，位置不变）。提交后按回读位置判定：大幅拖动后位置仍不在目标附近，则本会话改回只读进度，并经消息通道说明一次，不再保留假可拖的滑块。只读进度与可拖滑块在悬停时给出不同反馈，避免把不可控控件画成可控。
- 前端把交互草稿与已提交目标分开：拖动或方向键期间只改本地草稿，不发连续命令；松手或键盘提交时只发一次跳转。提交后短暂保留目标位置，收到提交之后、位置真的移动过且落在目标附近的系统样本才清掉目标，换歌、换会话或超时回到系统投影；旧请求的失败不清掉更新的目标。跳转成功后 UI 以重新读到的实际时间轴为准，不假定播放头精确落在请求值。
- 不使用网易云 CDP 做写操作：调试端口是客户端启动参数，选择器与页面结构随版本变化，且 ADR-0016 已明确 CDP 只作调试通道，不作为产品能力。

## 原因与职责边界

系统媒体控制是唯一对所有播放器一致的写通道；能力位与可跳转区间都来自同一份系统事实，前端不需要维护播放器黑名单。跳转是用户动作，命令只发一次，结果由回读校正，符合既有媒体动作「不排队重放」的约束。

原生负责能力判断、区间夹紧与结果回读；页面负责草稿、提交时机与投影校正。桌面音乐格子本轮不接跳转，仍沿用只读进度。

## 约束

- 不新增轮询：回读复用既有收敛请求与 `TimelinePropertiesChanged` 事件。
- 不新增颜色与控件样式：滑块轨道、已播填充与圆点只复用 `--fence-text` 混合，尺寸与只读进度条一致。
- 媒体动作仍共用同一个门闩，跳转与上一首、下一首、播放暂停互斥。

## 已知边界与待验证

- 真实播放器是否接受跳转、`MinSeekTime` / `MaxSeekTime` 的具体取值，以及时间轴事件到达时序都未在真机确认；网易云零时间轴会话通常拿不到可跳转量程，保持只读。
- 结果未确认时页面在 3 秒后回到系统投影，期间显示的是请求位置，不代表系统已落位。
- 键盘提交依赖滑块受控值与 `keyup`；连续按方向键只提交一次，最终位置以最后一次按键为准。
