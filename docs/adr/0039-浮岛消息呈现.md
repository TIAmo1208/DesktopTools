# 浮岛消息呈现

## 背景

浮岛当前只承载浮岛卡：音乐控制由插件声明 `island: true` 进入浮岛，卡片内容随三态切换。产品需要一个「系统消息」呈现面：新消息到达时常态胶囊给出简略信息，hover 给摘要与必要操作，展开给完整正文、来源与时间，消息消失或关闭后回落正常岛卡。

可用的消息源只有三类，取舍见下：

| 候选 | 结论 | 原因 |
| --- | --- | --- |
| 应用内通知（现有原生 Toast 队列） | 采用 | 队列、去重、期限与悬停暂停都已存在，是程序内唯一真实的消息通道 |
| 系统级通知（WinRT `UserNotificationListener`） | 不采用 | 当前发行版是 NSIS 当前用户安装，没有 MSIX 包身份，监听器不可用 |
| 媒体状态（SMTC） | 不采用 | 已经是浮岛卡，接进来只是重复既有呈现，不产生「消息」语义 |

## 决策

### 单一事实源

消息仍归原生 Toast 队列（`ToastManager`），浮岛只读投影，不另建第二份队列：

- 投影字段为 `id`、`type`、`content`、`source`、`loading`、`receivedAtMs`；`receivedAtMs` 在入队时取墙钟写入队列项，保证同一消息多次投影的显示时间一致。
- 投影只包含尚未进入离场的项：`closing` 为真即从投影移除，页面因此在关闭瞬间回落，不等待原生退出动画结束。
- 同来源同 `dedupeKey` 去重、每条消息的独立期限、悬停暂停、队列上限 `5`，全部沿用原生队列，浮岛不重复判定生命周期。

### 传输

- 命令 `get_island_messages` 返回当前投影，用于页面首次挂载与广播丢失后的补齐。
- 命令 `dismiss_island_message` 按 `id` 关闭单条消息，走与原生关闭按钮相同的 `ToastState::close` 路径，不另写离场逻辑。
- 事件 `island-messages-changed` 的载荷是完整投影数组。原生侧在每次刷新后比较投影，集合未变化（含只有动画推进的帧）不广播，避免逐帧事件。
- 浮岛不因消息来源失败而阻塞其他卡：订阅或首次读取失败时保留岛卡，展开态追加一个「消息通道不可用」状态卡，常态胶囊不被失败提示占用。

### 三态呈现

消息不是浮岛卡：不写入 `islandCardOrder`、不参与排序、不占 `maxTiles`、不在工作区快照与布局撤销内，也没有持久布局。

- 常态：最新一条消息占用胶囊，图标加一行正文，超出省略；胶囊高度规则不变，仍有且只有一个卡片区域。
- hover：最新一条的摘要（单行正文）与来源、时间，右侧给关闭按钮；高度仍是 `72`（左右贴边沿用胶囊高度），不出现完整正文。
- 展开：在岛卡之前逐条列出消息（最多 `5` 条，最新在前），给出可换行的完整正文、来源与时间与关闭按钮；消息卡不参与拖动排序，展开态不显示抓取光标。
- 阅读暂存：hover 与展开期间，即使后端已经关闭或过期该消息，页面仍把它留在当前视图，回到常态立即清空。这样短期限消息不会在阅读中被抽走，同时不改变原生队列的期限。

### 镜像取舍

同一条消息会同时出现在原生 Toast 与浮岛。本次接受这一重叠，不新增「关闭原生 Toast」开关：两者是同一队列的两个呈现面，浮岛负责留存与细读，原生 Toast 负责即时提醒。若后续要合并，应改原生可见性策略，而不是在浮岛侧过滤。

## 原因与职责边界

浮岛已经是独立呈现位，但它的数据来源是宿主能力而不是自己的领域。消息的去重、期限与离场都属于原生队列，浮岛只决定「此刻显示哪几条、每条显示到什么程度」。把事实留在 Rust、把呈现留给页面，避免两套过期判定在悬停、锁屏、全屏与拖动路径上分叉。

系统级通知需要 MSIX 身份，改打包模型超出本单范围；媒体状态已经是浮岛卡，再接入不会产生新的用户价值。

## 后果

- 浮岛页面多一条常驻订阅与一条关闭命令；消息集合变化会触发一次事件，但只在集合真正变化时发生。
- 页面在 hover/展开持有已消失消息的副本，最坏情况下展开态多留 5 条已过期消息，离开阅读态即回收。
- 关闭浮岛消息会同时关闭对应的原生 Toast；反过来关闭原生 Toast 也会让浮岛回落，两者共用同一身份。
- 消息与原生 Toast 的双显示是已知代价，接受度依赖真机观感。
- 浮岛在锁屏、全屏隐藏或截图期间仍可能持有消息投影（原生窗口隐藏不等于队列清空），恢复后按当时队列重新呈现。

## 待验证与待完成

- 三态切换下消息卡与音乐卡抢占胶囊的实际观感、消息卡在展开态的滚动与高度，尚未做真机验收。
- 原生 Toast 与浮岛同时显示同一条消息的接受度，需要在真实桌面与多显示器上确认。
- 消息读失败时「消息通道不可用」卡的实际出现频率与文案，未在真机上注入验证。
