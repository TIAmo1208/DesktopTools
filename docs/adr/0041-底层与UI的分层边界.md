# 底层与 UI 的分层边界

## 背景

`src/features/settings/` 现有 28 个 TS/TSX 文件、6354 行，平铺在一层目录里，同时承担三类互不相干的职责：

- 应用级基础设施：`PreferencesProvider.tsx` 在根层挂载、每个窗口一份，设置域外有 17 个文件经 `usePreferences` 引用，分布在 workspace、tiles、tile-content、island、desktop-items、components 六个域。
- 业务流：`WeatherSettings.tsx` 1010 行、`PluginSettingsPage.tsx` 1460 行，凭据草稿、验证会话、取消与迟到结果、安装队列、卸载与清单刷新都在渲染组件内完成。
- 可复用 UI 基元：`SettingsSwitch`、`SettingsInfo`、`SettingsCityList` 同时被设置页内部和页面之外使用。

Rust 侧是同一形状的问题：`workspace/mod.rs:16` 让领域层依赖 `app::settings::SettingsState`；`platform/windows/` 有 16 处直接读该状态、14 处直接调 `app::desktop_drop` 用例；`contracts/desktop_item.rs:76` 的 DTO 持有 `platform::windows::file_proof::FileProof`；`commands/mod.rs` 用 106 个分支的路由表跨四个领域。模块图存在四个环：workspace↔app、platform↔app、commands↔host、commands↔platform。

后果是改动放大、逻辑不可测、归属不可判断：偏好任一字段变化要穿过 Provider、设置页消费者与跨六个域的引用；天气会话与插件安装只能靠浏览器断言页覆盖；领域层测试必须构造真实 `SettingsState`。

## 决策

### 前端：UI 只做呈现，应用级设施归 `app`

- 全局偏好 Provider 位于 `src/app/preferences/`。它不属于任何功能域；功能域经 `usePreferences` 读取，不从设置目录导入。
- 每个 WebView 各持一份偏好实例，跨窗口只同步不可变契约（`preferences-changed` 事件与命令返回值），不共享内存。设置窗口是第二个前端客户端：共享契约，不共享运行时状态；偏好写入以 Rust 侧为权威。
- 领域流程（凭据草稿、验证会话、取消与迟到结果、安装队列、卸载与清单刷新）不驻留渲染组件。流程抽成 headless 模块，以 bridge 适配器为唯一外部依赖，由 `node:test` 覆盖；组件只保留布局、DOM 弹窗与事件绑定。
- 设置域按子域分目录。基元只在被两个以上功能域使用时上移；`SettingsCityList` 属于天气域，随天气子域走；`WeatherCityDialog` 与它不是重复实现，不合并。
- 文件长度不作为拆分依据，拆分理由只能是职责或归属（沿用 [ADR-0016](0016-正式项目架构.md)）。

### 后端：领域不依赖应用层，平台不编排用例

- 领域模块（workspace、weather、collect、component_runtime）不得 `use crate::app` 或 `crate::commands`；需要的偏好以只读快照经参数注入。
- `contracts` 不得依赖 `platform`；平台类型只留在平台层，DTO 只保留可序列化的判定结果。
- `platform` 只翻译 Win32、OLE 与 WebView2 事实，不选择业务模式、不编排用例。
- 命令边界只做来源白名单、参数校验、序列化与路由；领域用例路由按模块拆分，单张表不跨领域。

### 边界检查与基元清单

- 设置子域只经 `src/features/settings/ui/index.ts` 引用基元；`ui` 自身不依赖任何设置子域。公开清单为 SettingsSwitch、SettingsInfo、SettingsAbout、MusicSettingsRows 四个模块，新增基元要同时更新入口注释与本清单。
- 前端 feature 之间、设置子域之间、Rust 模块之间的依赖由 `scripts/检查架构边界.mjs` 以基线校验：存量依赖逐条登记在 `scripts/架构边界基线.json`，新增违规让 `test:scripts` 失败；修复一条依赖后同步删除对应基线项。
- Rust 规则：workspace 不得 use app/commands；contracts 不得 use platform/app/commands/host/workspace/shell；platform 不得 use app/commands；component_runtime 不得 use commands；weather 不得 use app。
- 前端规则：feature 之间只允许基线登记的依赖，设置子域之间只允许经 ui，设置页外壳可聚合全部子域。

### 实施顺序

1. 搬家：偏好 Provider 迁到 `src/app/preferences/`，全部引用路径更新，行为不变。
2. 抽逻辑：天气设置、插件设置抽 headless 模块；浏览器断言页保留为集成层。
3. 分目录：设置域按子域整理，基元给出公开清单。
4. 后端：偏好快照 → 命令路由 → 原生拖放用例 → 契约 proof → 主题解析。

每一步独立提交、独立验收；行为与用户可见文案不变。

## 影响

- 前端依赖方向收敛为 `app -> features -> bridge -> contracts`，功能域之间只经 `contracts`、`bridge`、`shared`；后端收敛为 `commands -> 领域 -> platform -> Windows`。
- 迁移期允许中间态（Provider 已迁出但主题模块仍在设置目录、天气流程一半在组件一半在 headless 模块）。每次提交必须保持可构建、可回归，并同步受影响的 README 与 ADR。
- 浏览器断言页不能删除：它们是真实 DOM 与样式的唯一证据；headless 单测只覆盖状态机，不替代断言页。

## 待验证

- 抽取后的 hook 测试与断言页分工是否覆盖现有回归面（天气会话取消、插件安装冲突队列、脚本重载）。
- 基元上移清单按实际跨域引用统计，未达到两个域的不上移。
- 后端偏好快照注入后，`desktop_host` 每帧路径与浮岛策略调用的额外开销。
- 机器可拦截的边界规则（Rust `use` 扫描、前端 import 扫描）尚未落地，当前以评审约束代替。
