# 前端与实现约定

改代码前读本页。构建、命令与门禁见 `docs/agents/构建运行.md`；样式归属见 `docs/design/CSS约定.md`。

## 计划与执行

- 制定计划前检查当前项目状态，给出完整、可执行的方案；实现功能前先追踪真实实现路径、调用链和关键依赖，以查证结果确定修改方式。
- 添加功能前，先检查当前项目是否已有对应能力。已有能力必须沿用其真实实现路径、交互逻辑和视觉规则，并保持现有职责边界；当前实现未覆盖的功能，先提出可执行方案、说明影响与取舍，取得用户确认后再实现。
- 在已有功能上扩展内容时，优先将新增项纳入原有的数据结构、列表或映射、组件层级、状态管理、持久化链路和样式规则；不得为了减少改动而在既有结构外追加旁路渲染、专用布局补丁或重复状态。若确需例外，必须说明现有结构无法承载的具体原因，并同步补齐类型、默认值、调用方、校验、测试和文档。
- 遇到需要用户决策的节点时，提供多种可选方案，并说明各自的适用场景、影响和取舍。
- 设计功能时，优先选择资源占用低、运行时开销小的实现方案，避免持续轮询、重复计算、无效渲染和不必要的常驻资源。
- 对需要持续更新的功能，优先采用事件驱动的被动响应式更新；只有在缺少可靠事件源时才使用轮询，并限制轮询频率、作用范围和生命周期。

## 异步回调与生命周期状态

- 注册窗口关闭、原生事件、定时器、观察器或订阅等长生命周期回调时，不得直接依赖只在注册时捕获的 React 状态；回调需要读取的 `ready`、`dirty`、`busy`、权限或关闭许可等可变状态，使用 `useRef` 保存最新值，或让完整依赖变化时重新注册回调。
- React state 负责渲染，ref 负责命令式回调读取；异步操作开始、成功、失败和清理时同步更新两者，避免出现“实例已存在但状态仍为初始值”的状态门槛。
- 生命周期回调的清理函数必须移除订阅并重置相关 ref；涉及异步提交时，同时防止重复提交、迟到回调和关闭重入。
- 修复此类问题时，先用唯一前缀日志或最小回归测试记录“回调触发、状态快照、分支选择、异步结果、销毁结果”五个节点；根因确认后删除临时日志，并保留可重复的受影响测试或手工验收步骤。
