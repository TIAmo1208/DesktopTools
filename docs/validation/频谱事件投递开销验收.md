# 频谱事件投递开销验收

## 结论与范围

Release 构建下，频谱开启相对停止采集的进程 CPU 增量在本机 5 个样本间为 0.31–1.25 个百分点，中位数 0.42，全部低于工单的 1.5 个百分点目标；其中采集与分析线程占 0.42–0.62，其余为主线程投递唤醒。

Debug 构建测得同一管线的增量约 1.3–1.5 个百分点，进程级读数还会波动到 4 个百分点；工单记录的「当前 3.4」是 Debug 构建未优化 FFT 与测量噪声叠加的结果，不能当作发布版口径。

两项投递侧改动的实测结论：

- 按显示器过滤：投递次数确定性减半（有音乐控件屏 29.7 帧/秒，无该控件的屏 0 帧/秒，Debug 与 Release 均复核），对 CPU 增量的贡献在 0.1 个百分点以内。
- 采集缓冲改定长环形窗口：回环回调 47 微秒/次 → 35 微秒/次（Debug 计时口径），已保留。
- 投递改走 WebView2 `PostWebMessageAsJson`：单宿主单帧 58 微秒，比原有 `evaluate_script` 的 47 微秒更慢，未采用；页面侧监听在文档创建早期取不到 `chrome.webview`，需要延后重试，进一步增加复杂度。

## 方法

Debug 口径：`build/target/debug/desktop-tools.exe` + `npm run dev` 页面，用于阶段计时与改动前后对比。Release 口径：`npm run tauri:build` 生成的 `build/target/release/desktop-tools.exe`，页面由内嵌协议加载，用于增量验收。

设备为 AMD Ryzen 5 5600G、12 个逻辑处理器、双 2560×1440 显示器；音乐控件只位于 DISPLAY1，采集设备为 USB 声卡 `DX3 III`，16 段、30fps（工单原始参数 24 段，本轮未复测）。

三种取数口径：

1. 进程累计 CPU：`TotalProcessorTime` 差分除以窗口时长。
2. 按线程 CPU：`GetThreadTimes` 差分，窗口 30 秒。采集与分析线程只在采集运行时存在，因此「只在运行窗口出现的线程」直接对应采集、分析、发布开销；稳定线程的增量对应投递唤醒。
3. 阶段耗时：临时在采集回调、分析、`app.emit`、主线程投递任务与单宿主脚本求值处插入 `Instant` 计时，每 150 帧输出一次窗口均值；计时、环境开关与临时计数代码在收尾前全部删除。

Release 验收用 60 秒静音 WAV 循环播放，让 WASAPI 回环保持真实回调节奏；静音数据不改变 FFT 计算量，但柱高为零会减少绘制，渲染侧读数因此略低于真实音乐场景。会话锁屏会同时停止发布与绘制，只用于采集侧对比。

## 结果

阶段耗时（16 段、30fps、Debug 构建，窗口内均值）：

| 阶段 | 改动前 | 改动后 |
| --- | --- | --- |
| 采集回调（约 505 次/5 秒窗口） | 47 微秒/次 | 35 微秒/次（环形窗口） |
| FFT 分析与分段 | 242–254 微秒/帧 | 245 微秒/帧（未改） |
| `app.emit` 发布（含监听同步派发） | 73–77 微秒/帧 | 74 微秒/帧（未改） |
| 主线程投递任务（含过滤与脚本构造） | 71 微秒/帧 | 71 微秒/帧（未改） |
| 单宿主脚本求值 `evaluate_script` | 47 微秒/帧 | — |
| 单宿主消息投递 `PostWebMessageAsJson` | — | 58 微秒/帧（未采用） |

Release 进程增量（每个样本为「采集运行 30 秒」与「同一进程停止采集 30 秒」的按线程合计差值）：

| 样本 | 运行窗口 | 停止窗口 | 增量 | 占单核 |
| --- | --- | --- | --- | --- |
| 1（无静音流） | 594 毫秒/30 秒 | 219 毫秒/30 秒 | 375 毫秒 | 1.25% |
| 2（无静音流） | 375 毫秒 | 281 毫秒 | 94 毫秒 | 0.31% |
| 3（静音流） | 297 毫秒 | 172 毫秒 | 125 毫秒 | 0.42% |
| 4（静音流） | 563 毫秒 | 234 毫秒 | 328 毫秒 | 1.09% |
| 5（静音流） | 344 毫秒 | 219 毫秒 | 125 毫秒 | 0.42% |

Debug 进程级样本（60 秒窗口，同一进程成对比较）：采集运行、暂停发布 1000 毫秒 vs 停止 125 毫秒（1.46 个百分点）；改动前后各三轮 10 秒窗口均值 4.17% 与 3.96%，差值小于轮次波动。

投递计数：Debug 改动前两屏各 29.8 帧/秒；改动后仅有音乐控件的屏 29.7 帧/秒、另一屏 0；Release 复核 29.7 帧/秒与 0，载荷 16 段非零数据。

## 判断与后续

1. 保留按显示器过滤与环形窗口：语义正确、回调耗时下降约 25%，但都不承担主要降耗指标。
2. 不采用 `PostWebMessageAsJson`：实测单帧调用更慢，页面侧还要处理通道就绪时序。
3. 工单的 1.5 个百分点目标在 Release、16 段、30fps 下成立（中位数 0.42，最差 1.25）。剩余成本主要是采集回调与每帧分析、发布、主线程唤醒；继续优化需要改事件频率或采集格式，属于行为变更，应先确认。
4. 工单原文的 3.4 个百分点应按 Release 口径重写，避免继续用 Debug 数字评估发布版本。

## 尚未完成的验收

- 24 段、真实音乐播放的 Release 增量未测；本轮为 16 段，静音流绘制负载偏低。
- 解锁状态下的端到端验证覆盖投递计数与数据长度，未做同曲峰值差异 <5% 的定量比对；暂停/切屏/宿主重建后的连续性与不丢帧未逐项回归。
- 两屏同时存在音乐控件、设备热插拔、长时间 CPU 与内存趋势未测。
- Release 增量样本分散在 0.31–1.25 之间，需要更多轮次或长期按线程采样才能收紧区间。

原始样本见 `build/validation/频谱事件投递开销-原始数据.csv`。
