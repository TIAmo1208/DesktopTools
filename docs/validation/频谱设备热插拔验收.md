# 频谱采集设备热插拔验收

## 结论与范围

设置页「频谱采集设备」列表与频谱采集目标改为由 Windows Core Audio 端点通知驱动，不再由前端每 2 秒轮询、采集线程每 2 秒自查。本轮在本机验证：

- 停留在「音乐控制」面板时，插入/拔出 USB 声卡后设备列表在端点变化后约 0.27 秒内更新（两次取样为 0.267 秒与 0.267 秒；另有两次更新早于 50 毫秒粒度的系统轮询观察到变化）。
- 拔出正在采集的设备后，采集在约 0.22 秒内回退到系统默认设备，`audio-spectrum-device-changed` 已到达前端；重新插入并成为系统默认后同样即时切回。
- 关闭面板与设置窗口、关闭频谱后，通知监听线程释放；重新打开后按需重建。
- 进程 CPU 前后对比：事件驱动版本 120 秒 0.76%（单核），被替换的 2 秒轮询版本 0.81% 与 0.95%；差异在 0.2 个百分点以内，属测量噪声量级。轮询确实存在，但成本很小，本次收益主要是延迟不再依赖轮询周期。

## 方法

- 环境：Windows 11，AMD Ryzen 5 5600G（12 逻辑处理器），Debug 构建 `build/target/debug/desktop-tools.exe` + `npm run dev` 页面；被测设备为 USB 声卡 `DX1 II`，本机另有板载 `Digital Audio (S/PDIF)` 作为回退目标。
- 事件取证：通过 WebView2 远程调试连接设置窗口，在页面内注入观察器，每 100 毫秒记录「频谱采集设备」下拉框选项集合与时间戳，同时用 Tauri 事件接口订阅 `audio-spectrum-device-changed`。
- 系统侧取证：PowerShell 每 50 毫秒枚举一次 `Get-PnpDevice -Class AudioEndpoint -Status OK` 的渲染端点集合，记录集合变化时刻，与页面时间戳同机对比。
- 采集侧取证：应用日志的「采集设备切换为…」「重建采集失败」行，按秒对齐。
- CPU 对比：同一进程、同一设置面板打开、频谱关闭（排除 4% 量级的采集开销），用 `Get-Process` 累计 CPU 差分除以窗口时长，窗口 120 秒；把设置页临时换回上一次提交的 2 秒轮询实现作为对照，测完恢复。

## 结果

### 列表更新与采集切换（系统端点时刻 → 页面时刻）

| 动作 | 系统端点变化 | 设置页列表更新 | 采集切换事件 |
| --- | --- | --- | --- |
| 拔出 DX1 II | 10:07:30.411 | 10:07:30.678（+267 毫秒） | 10:07:30.630（+219 毫秒，切到 S/PDIF） |
| 插回 DX1 II | 10:07:36.704 | 10:07:36.667（早于系统轮询） | 10:07:36.667（切回 DX1 II） |

修复前同一动作的另一轮取样（10:03:41、10:03:47、10:03:54、10:04:01）列表更新分别为 +0 至 −181 毫秒（即更新时刻与系统轮询同刻或更早），说明列表更新已不依赖固定轮询周期。

### 生命周期

- 关闭「显示实时频谱」：10:11:27「频谱采集已停止」，监听线程保留（面板仍打开）。
- 关闭设置窗口：10:12:01「设备通知监听已停止」与「窗口已销毁，页面资源已释放」相邻出现，说明设置页持有的监听已释放。
- 重新打开设置并开启频谱：10:13:02「设备通知监听已启动」，10:13:04「频谱采集已启动」，按需重建。

### CPU 对比（120 秒，设置面板打开，频谱关闭）

| 实现 | 采样 1 | 采样 2 |
| --- | --- | --- |
| 事件驱动（本次） | 0.906 CPU 秒 = 0.76% 单核 | — |
| 2 秒轮询（被替换） | 1.141 CPU 秒 = 0.95% 单核 | 0.969 CPU 秒 = 0.81% 单核 |

轮询版本每次枚举约消耗 4 毫秒 CPU（60 次/120 秒，差值约 0.2 CPU 秒），与上表差值一致。

## 实现要点

- 新增 Core Audio 端点通知客户端，回调只向通道写信号；监听线程去抖 300 毫秒后重新枚举，仅在列表真正变化时投递 `audio-devices-changed`，并推进设备代数。
- 监听线程与采集线程各自持有一个开关，全部关闭后注销回调并退出；设置窗口销毁时复位设置页开关。
- 采集线程不再自查设备，按设备代数重建；保留 10 秒兜底检查。重建失败按 0.5 秒起步、上限 2 秒退避重试。
- 旧设备已失效或目标就是同一设备时先释放旧流；切换到另一台可用设备时先建新流，失败时保留现有出图。
- 采集流回调只在 `DeviceNotAvailable` / `StreamInvalidated` 时标记重建，避免缓冲欠载触发无意义重建。

## 判断与后续

1. 事件驱动保留：列表与采集切换均在同一批通知内完成，不受轮询周期约束；实现只在设置面板或采集运行期间存在。
2. 拔出设备后的首次重建偶尔仍返回 `RPC_E_CHANGED_MODE`（0x80010106）。已确认与调用线程套间无关（强制多线程套间后仍出现），属于端点刚变化时的瞬时失败；退避重试可恢复，且失败期间旧流继续出图。修复前同场景会永久失败，本次线程内创建设备对象后已不再复现永久失败。
3. 保存指定设备（非「跟随系统默认」）时的「保留保存值 + 回退系统默认」路径本轮未单独复测；其设备解析逻辑未改动。
4. 连续 20 次拔插的句柄泄漏与通知风暴未测；本轮为 4 次插拔。

## 尚未完成的验收

- 20 次连续拔插、长时间运行后的句柄与线程趋势未测。
- 蓝牙等延迟枚举的设备未覆盖；本轮只有 USB 声卡与板载端点。
