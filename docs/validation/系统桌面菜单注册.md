# 系统桌面菜单注册

## 最终结论

**状态：实机验收通过。** 2026-09-08，用户在恢复 Explorer 原生桌面菜单后确认“都没问题”。本次确认关闭桌面空白处原生菜单显示、新建 TXT 及本轮菜单使用的待验收项；不扩大为所有 Shell 动词、第三方扩展或跨 Windows 版本均已逐项验证。

最终采用的职责划分：

1. Desktop Tools 接收空白处右键，将屏幕坐标随 `WM_CONTEXTMENU` 投递给 Explorer 的真实 `SHELLDLL_DefView`。
2. Explorer 自己创建、显示原生桌面菜单并执行系统命令，保留真实桌面上下文。
3. 产品入口由当前用户的 `DesktopBackground` 注册表声明；Explorer 读取注册项生成 Desktop Tools 子菜单。
4. 产品动作通过固定启动参数回传给单一主实例，异步进入现有布局、刷新和设置业务入口。

不恢复跨进程获取 Explorer `IContextMenu` 的路径，也不以 Desktop 文件夹背景菜单加桌面扩展的拼接方案替代真实桌面菜单。旧 `0x80004005` 的具体内部根因仍未确定；最终方案绕开了该失败调用路径，用户实机确认新建 TXT 正常，不能将“故障已解决”写成“已证明旧根因”。

## 实现边界

按用户要求先把 Desktop Tools 产品菜单注册到系统原生桌面右键菜单，不再在获取背景菜单后通过 `AppendMenuW` 追加产品子菜单。

后续用户要求先还原系统原生桌面菜单：空白处右键现已改为重新发现 Explorer 的 `SHELLDLL_DefView`，投递 `WM_CONTEXTMENU`，由 Explorer 自己生成菜单及执行命令。正式背景路径不再取得 `IContextMenu`、拼接文件夹菜单或执行 `InvokeCommand`。项目和围栏菜单仍保留依赖选择状态的原有实现。

前端对背景菜单请求不再立即抢回焦点。消息投递成功只代表 Explorer 收到请求，不代表菜单已显示或命令执行成功；独立验收 `background_menu_is_owned_by_explorer` 检查实际菜单窗口属于 Explorer 进程。屏幕坐标按 Win32 有符号 16 位协议打包并校验，支持主屏左侧、上方副屏，超出协议范围时报错。

原生窗口归属验收、负坐标显示器坐标测试、前端 `npm run typecheck`、严格 Clippy 与 `git diff --check` 均已通过；随后获得上述用户实机确认。旧文件夹菜单获取函数仅保留在 `cfg(test)` 下作为历史诊断对照，不进入正式背景菜单执行路径。

## 注册与命令路径

注册范围仅为当前用户，无需管理员权限：

```text
HKCU\Software\Classes\DesktopBackground\shell\DesktopTools
    MUIVerb = Desktop Tools
    SubCommands = ""
    Icon = "<程序路径>",0
    shell\00-create-fence\command
    shell\01-edit-layout\command
    shell\02-refresh\command
    shell\03-settings\command
```

四个子项依次显示“新建围栏、编辑布局、刷新桌面项目、打开设置”。Explorer 根据注册表创建级联菜单，各项启动命令为：

```text
"<程序路径>" --desktop-menu <固定动作>
```

- 启动参数只接受四个固定动作，不接受任意 Shell 命令。
- 已有实例时，辅助进程通过当前 Windows 会话中的消息窗口回传数字动作，收到确认后退出，不创建 Shell STA、WebView 或 guardian。
- 没有实例时启动程序，完成工作区初始化后执行初始动作。命名互斥体覆盖启动过程，防止连续点击产生多个桌面宿主。
- 新建围栏、刷新沿用现有命令与事件发布路径；新建位置使用执行时的指针位置，并转换为对应显示器的 CSS 坐标。“编辑布局”沿用当前始终可编辑的行为，“打开设置”复用托盘窗口显隐接口。
- 正常启动更新注册表中的可执行文件路径。退出保留注册项，便于下次从原生菜单启动。

## 安装与移除

```powershell
.\build\target\debug\desktop-tools.exe --register-desktop-menu
.\build\target\debug\desktop-tools.exe --unregister-desktop-menu
```

两个命令处理完立即退出。移除只删除本产品专属键，不删除其他软件的菜单。正常启动会重新登记；当前未增加永久禁用设置或安装包卸载钩子。

### 实施证据与历史诊断

- 当前用户注册表中已实际写入四个动作及带引号的程序路径。Shell 原生桌面菜单枚举已确认出现 `Desktop Tools`。
- 注册动词 `--desktop-menu refresh` 实测辅助进程返回 0，主进程编号保持不变。
- 上述首次回传暴露 `0x8001010D`：Tauri 的 `run_on_main_thread` 在已经位于主线程时立即执行，导致刷新中的跨进程 COM 调用仍处于 `SendMessage` 栈内。已改为 `PostMessage` 二次投递后执行，独立于同步接收确认。
- 修复后实测：主进程 `1316` 保持不变，辅助进程返回 0，`16:27:10` 日志确认刷新动作完成，未再出现首次回传的 COM 警告。最终 `cargo build --bin desktop-tools` 通过。
- 完整常规 Rust 测试 78 项通过；严格 Clippy 通过。
- **历史诊断测试的限制**：`registered_desktop_menu_is_loaded_by_shell` 在独立 Shell 视图中能枚举顶层入口，但子菜单为空；该测试曾失败，不能改记为自动通过。`IContextMenu3`、同步级联标志和根菜单初始化未解决，尝试 `ExtendedSubCommandsKey` 也无差异，注册最终保留 `SubCommands` 空串与父项下 `shell` 子动词。最终采用真实 Explorer 菜单后用户已确认正常，该独立视图测试不再作为实际桌面菜单的发布门槛；其测试宿主差异仍未查明。

## API 与 GitHub 调查

- [微软：静态级联菜单](https://learn.microsoft.com/en-us/windows/win32/shell/creating-static-cascading-menus)：Windows 7 起支持注册表声明菜单，静态方法不足时才需要 COM 实现。
- [微软：ExtendedSubCommandsKey](https://learn.microsoft.com/en-us/windows/win32/shell/how-to-create-cascading-menus-with-the-extendedsubcommandskey-registry-entry)：说明 HKCU\Software\Classes 的无提权注册与父项下静态子动词布局。
- [微软：SubCommands](https://learn.microsoft.com/en-us/windows/win32/shell/how-to--create-cascading-menus-with-the-subcommands-registry-entry)：说明级联菜单的注册方式。
- [微软 GitHub：InvokeCommand 文档](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/shobjidl_core/nf-shobjidl_core-icontextmenu-invokecommand.md)：不识别的动词或命令编号也可返回 `E_FAIL`；Unicode 需要 `CMINVOKECOMMANDINFOEX` 与对应标志。因此 `0x80004005` 本身不能证明缺少文件夹上下文。
- [微软 GitHub：Shell 菜单样例](https://github.com/microsoft/Windows-classic-samples/blob/master/Samples/Win7Samples/winui/shell/shellextensibility/explorerdataprovider/ContextMenu.cpp)：包含 `IShellExtInit`、`IObjectWithSite` 及菜单偏移解释，适合作为后续检查初始化上下文和动词路由的参考。

未找到足以直接解释本项目“独立 IShellView 新建 TXT 返回 0x80004005”的同条件 GitHub 问题。若以后专门调查历史路径，应记录具体 handler、命令偏移与 canonical verb、初始化 PIDL、site 查询结果及线程模型，不能把样例中的失败条件直接认定为本项目根因。该调查不再阻塞已经实机验收通过的 Explorer 菜单方案。
